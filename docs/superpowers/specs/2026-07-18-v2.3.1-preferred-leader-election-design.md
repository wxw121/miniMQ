# V2.3.1 Preferred Leader Election Design / V2.3.1 Preferred Leader 选举设计

**Status / 状态：** Approved for implementation / 已批准实施  
**Scope / 范围：** `R3-P1-01` only / 仅 `R3-P1-01`

## 1. Goal / 目标

When an active partition leader is marked offline, elect the first surviving ISR replica in the partition's configured `replicaBrokerIds` order. Do not elect by numeric broker ID order.

当活跃分区 Leader 被标记离线时，按照分区配置的 `replicaBrokerIds` 顺序，选举第一个仍在 ISR 中的存活副本，不再按照 Broker ID 数值大小选举。

## 2. Scope Boundary / 范围边界

This change implements preferred-order election only. It does not compare replica log-end offsets, add ISR lag management, persist follower LEO state, or introduce a general election-policy abstraction.

本次变更只实现 preferred 顺序选举，不比较副本日志末端位点，不增加 ISR 滞后管理，不持久化 follower LEO，也不引入通用选举策略抽象。

`R3-P1-07` remains deferred until `R3-P1-06` provides a reliable Controller-visible LEO source. Combining those items later avoids coupling Controller decisions to transient, broker-local `ReplicaStateManager` state.

`R3-P1-07` 保持延期，待 `R3-P1-06` 提供 Controller 可可靠访问的 LEO 数据源后一起实现。这样可以避免 Controller 的选举决策依赖临时、Broker 本地的 `ReplicaStateManager` 内存状态。

## 3. Selection Semantics / 选择语义

For each partition whose leader is being marked offline:

1. Treat the offline Broker as unavailable before selecting a replacement.
2. Iterate `replicaBrokerIds` in stored order.
3. Select the first Broker ID that remains in `isrBrokerIds`, is not the offline Broker, and is currently online.
4. Reject the entire `markBrokerOffline` operation with `INVALID_REQUEST` if any affected leader partition has no replacement.
5. Apply no metadata mutation when validation fails.

对于 Leader 正在被标记离线的每个分区：

1. 选择替代者前先把待离线 Broker 视为不可用。
2. 按保存顺序遍历 `replicaBrokerIds`。
3. 选择第一个仍在 `isrBrokerIds`、不是待离线 Broker 且当前在线的 Broker ID。
4. 如果任一受影响的 Leader 分区没有替代者，整个 `markBrokerOffline` 操作返回 `INVALID_REQUEST`。
5. 预校验失败时不修改任何元数据。

The ISR list must not be numerically sorted as part of election. Its membership changes only by removing the offline Broker in this operation.

选举过程中不得按数值排序 ISR 列表。本次操作对 ISR 成员关系的唯一修改是移除离线 Broker。

## 4. Implementation Shape / 实现结构

Keep the behavior inside `ClusterController`:

- Add one private helper that returns the preferred surviving leader for a partition and offline Broker ID.
- Use that helper during the validation pass to preserve the existing validate-all-then-mutate atomicity.
- Use the same helper result during the mutation pass, so validation and application cannot disagree.
- Do not add new public APIs or cross-module dependencies.

实现保持在 `ClusterController` 内部：

- 增加一个私有辅助方法，根据分区和待离线 Broker ID 返回 preferred 存活 Leader。
- 在预校验阶段使用该方法，保持现有“全部校验后再修改”的原子性。
- 在变更阶段复用相同选择语义，避免校验与应用结果不一致。
- 不增加新的公开 API 或跨模块依赖。

## 5. Test Strategy / 测试策略

Use TDD in `ClusterControllerTest`:

1. Create or inject partition metadata whose replica preference order differs from numeric Broker ID order, for example replicas `[2, 1, 0]` with all three members in ISR and Broker `2` as leader.
2. Mark Broker `2` offline.
3. Assert that Broker `1` becomes leader. The current implementation sorts ISR and elects Broker `0`, so this test must fail before production code changes.
4. Assert that the remaining ISR order is `[1, 0]`.
5. Run existing tests covering last-ISR rejection, atomic non-mutation, and offline-replica normalization.
6. Run the full Maven verification and retain the 90% line-coverage gate.

在 `ClusterControllerTest` 中使用 TDD：

1. 创建或注入副本偏好顺序与 Broker ID 数值顺序不同的分区元数据，例如副本为 `[2, 1, 0]`，三个成员都在 ISR，Broker `2` 为 Leader。
2. 将 Broker `2` 标记为离线。
3. 断言 Broker `1` 成为 Leader。当前实现会排序 ISR 并选举 Broker `0`，因此测试必须在修改生产代码前失败。
4. 断言剩余 ISR 顺序为 `[1, 0]`。
5. 运行现有测试，覆盖最后一个 ISR 拒绝离线、失败时原子不修改，以及离线副本不会被 normalize 恢复。
6. 运行完整 Maven 验证并保持 90% 行覆盖率门禁。

## 7. Completion Criteria / 完成标准

The work is complete when the focused test fails before implementation, passes after the minimal Controller change, all existing tests pass, Maven verification passes, line coverage remains at least 90%, and public roadmap/review documentation reflects the final status.

当聚焦测试在实现前按预期失败、最小 Controller 修改后通过、所有现有测试通过、Maven 完整验证通过、行覆盖率保持至少 90%，且公开路线图与审查文档同步最终状态时，本项工作才算完成。
