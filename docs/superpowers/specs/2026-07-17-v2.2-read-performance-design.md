# MiniMQ V2.2 Read Performance Design / MiniMQ V2.2 读取性能设计

**Status / 状态：** Approved for specification review / 已批准进入规格复核

**Goal:** Move the project to `2.2.0-SNAPSHOT` and add an end-to-end Broker
FETCH sendfile path that builds on segmented logs, sparse indexes, retention,
compaction, and the existing heap-buffer fallback.

**目标：** 将项目版本推进到 `2.2.0-SNAPSHOT`，并在现有分段日志、稀疏索引、
retention、compaction 和堆内 buffer 回退路径之上，实现端到端 Broker FETCH
sendfile 快速路径。

## Scope / 范围

V2.2 includes:

V2.2 包含：

1. A storage-level fetch plan that describes stable byte ranges in one or more
   segment log files without materializing record payloads.
   存储层提供 FETCH 计划，用于描述一个或多个 segment 日志文件中的稳定字节区间，
   且不实例化记录 payload。
2. Sparse-index positioning followed by record-metadata scanning to compute the
   first eligible record, record count, byte budget, and contiguous file spans.
   先用稀疏索引定位，再扫描记录元数据，计算第一条符合条件的记录、记录数、字节预算
   和连续文件区间。
3. A Broker writer that emits a MiniMQ FETCH frame prefix followed by Netty
   `DefaultFileRegion` objects backed by read-only `FileChannel` instances.
   Broker 先写 MiniMQ FETCH 帧前缀，再写由只读 `FileChannel` 支撑的 Netty
   `DefaultFileRegion`。
4. Reader-lease integration that keeps catalog and segment files stable until
   the asynchronous network write completes, fails, times out, or the channel
   closes.
   读租约一直保持 catalog 与 segment 文件稳定，直到异步网络写完成、失败、超时或
   channel 关闭。
5. `AUTO` and `HEAP` transfer modes, compatibility fallback, transfer metrics,
   an opt-in end-to-end benchmark, and synchronized project documentation.
   提供 `AUTO` 与 `HEAP` 传输模式、兼容回退、传输指标、可选端到端 benchmark，
   并同步项目文档。

The wire protocol version and record encoding remain unchanged. mmap, TLS
zero-copy, replication, service discovery, circuit breaking, Epoll, producer
sendfile, persistent metrics, and a new admin protocol are excluded.

线协议版本与记录编码保持不变。不包含 mmap、TLS 零拷贝、副本、服务发现、熔断、
Epoll、Producer sendfile、持久化指标和新的管理协议。

## Alternatives Considered / 备选方案

1. **Chosen: Netty `DefaultFileRegion` backed by `FileChannel.transferTo`.** The
   segment record bytes already match the FETCH record wire layout
   (`offset + keyLength + key + valueLength + value`), so the Broker only needs
   to allocate the frame and response prefix. This is the only option considered
   that removes the payload copy from the end-to-end Broker network path.
   **选定方案：使用基于 `FileChannel.transferTo` 的 Netty
   `DefaultFileRegion`。** segment 记录字节与 FETCH 线协议记录布局一致，因此
   Broker 只需分配帧头和响应前缀；该方案能真正移除端到端 Broker 网络路径中的
   payload 复制。
2. mmap indexed local reads would reduce file-read system calls, but the current
   API would still allocate record arrays and copy them into a response
   `ByteBuf`. It does not satisfy the end-to-end requirement.
   mmap 索引读取可减少文件读取系统调用，但当前 API 仍需分配记录数组并复制到响应
   `ByteBuf`，不满足端到端目标。
3. Pooled direct buffers and gathering writes would improve allocation behavior
   and work through TLS, but they retain the file-to-userspace copy. They remain
   a possible future heap-fallback optimization.
   池化 direct buffer 与 gathering write 可改善分配并兼容 TLS，但仍保留文件到
   用户态的复制，可作为未来 heap 回退路径的优化。

## Architecture And Component Boundaries / 架构与组件边界

`mq-storage` remains independent of Netty. A new
`TransferablePartitionLog` capability exposes
`FetchPlan planFetch(long fromOffset, int maxBytes)`. `SegmentedPartitionLog`
implements the capability in addition to `PartitionLog`; the legacy
`FilePartitionLog` does not and therefore uses the heap path.

`mq-storage` 继续不依赖 Netty。新增 `TransferablePartitionLog` 能力并暴露
`FetchPlan planFetch(long fromOffset, int maxBytes)`。`SegmentedPartitionLog`
在实现 `PartitionLog` 的同时实现该能力；旧 `FilePartitionLog` 不实现，因此使用
heap 路径。

`FetchPlan` is an idempotently closeable immutable view containing:

`FetchPlan` 是可幂等关闭的不可变视图，包含：

- the fetch high watermark / 本次 FETCH 的 high watermark；
- the record count and encoded record bytes / 记录数与编码后记录字节数；
- ordered `FileRegionSlice(Path path, long position, long length)` values /
  有序的 `FileRegionSlice(Path path, long position, long length)`；
- an internal reader lease released by `close()` / 由 `close()` 释放的内部读租约。

`SegmentFile.planRead` uses `SparseOffsetIndex.floorPosition(fromOffset)` and a
metadata-only scanner in `PartitionLogRecordCodec`. The scanner reads offsets
and length fields, validates the same corruption boundaries as heap decoding,
and skips key/value payload positions without allocating arrays. Each selected
segment contributes at most one contiguous slice.

`SegmentFile.planRead` 使用 `SparseOffsetIndex.floorPosition(fromOffset)` 和
`PartitionLogRecordCodec` 中只扫描元数据的 reader。该 reader 读取 offset 与长度
字段，执行与 heap 解码相同的损坏校验，并通过移动位置跳过 key/value payload，
不分配数组。每个选中的 segment 最多产生一个连续 slice。

`mq-protocol` adds a FETCH-prefix encoder. It writes the normal frame header,
response header, topic, partition, high watermark, and record count while the
frame length includes the following file-region bytes. It has no dependency on
storage types.

`mq-protocol` 新增 FETCH 前缀编码器。它写入正常帧头、响应头、topic、partition、
high watermark 和记录数；帧长度预先包含后续 file-region 字节。协议层不依赖存储
类型。

`mq-broker` adds `FetchResponseWriter`, which bridges a `FetchPlan` to Netty.
It opens all read-only channels before writing the prefix, queues the prefix and
ordered `DefaultFileRegion` values on the channel event loop, and owns cleanup,
timeout, fallback, and metrics. `MqRequestHandler` retains request decoding and
leader validation and delegates only successful FETCH responses to this writer.

`mq-broker` 新增 `FetchResponseWriter`，负责把 `FetchPlan` 桥接到 Netty。它在
写前缀前打开全部只读 channel，在 channel event loop 上依次排入前缀和有序
`DefaultFileRegion`，并负责清理、超时、回退和指标。`MqRequestHandler` 保留请求
解码与 leader 校验，只把成功的 FETCH 响应委托给该 writer。

## Fetch Data Flow / FETCH 数据流

1. The request handler decodes the request and validates the partition leader.
   请求 handler 解码请求并验证分区 leader。
2. The writer selects heap or sendfile before any response bytes are emitted.
   writer 在发出任何响应字节前选择 heap 或 sendfile。
3. Sendfile planning acquires the existing reader gate, then captures catalog
   generation, ordered segment references, and high watermark in one short
   critical section. The high watermark is the exclusive scan boundary.
   sendfile 规划先获取现有 reader 门禁，再在一个短临界区中固定 catalog
   generation、有序 segment 引用与 high watermark；high watermark 是扫描上界。
4. The starting segment is selected by base offset. Its sparse index supplies a
   floor file position, and metadata scanning advances to the first physical
   record whose offset is at least the requested offset.
   通过 base offset 选择起始 segment；稀疏索引给出 floor 文件位置；元数据扫描
   前进到第一条 offset 不小于请求 offset 的物理记录。
5. Planning walks segments until the existing record-byte budget is satisfied.
   Compaction holes are skipped, an offset older than `logStartOffset` begins at
   the first retained record, and at least the first eligible record may exceed
   `maxBytes`, matching the current heap behavior.
   规划跨 segment 前进直到满足现有记录字节预算。跳过 compaction 空洞；早于
   `logStartOffset` 的请求从第一条保留记录开始；第一条符合条件的记录即使超过
   `maxBytes` 也允许返回，与当前 heap 行为一致。
6. Later appends may continue, but their bytes are beyond the captured high
   watermark and cannot enter the plan. Segment rolling is allowed; retention
   and compaction mutation is not.
   后续 append 可以继续，但其字节位于已捕获 high watermark 之后，不会进入当前
   计划。允许 segment rolling，不允许 retention 或 compaction 修改文件。
7. The Broker opens all planned files, encodes the prefix with the final frame
   length, queues the prefix followed by the file regions, and flushes the last
   write. Writes from later requests are queued after the complete response.
   Broker 打开全部计划文件，用最终帧长度编码前缀，然后排入前缀和各 file region，
   并在最后一次 write 时 flush。后续请求的写操作排在整个响应之后。
8. The final future listener cancels the timeout, closes owned file regions, and
   closes the plan. Cleanup is idempotent across success, failure, timeout, and
   channel-close paths.
   最终 future listener 取消超时、关闭自有 file region 并关闭计划。成功、失败、
   超时和 channel 关闭路径上的清理均为幂等。

## Retention And Compaction Contract / Retention 与 Compaction 契约

The existing V2.1 reader-quiescence contract remains authoritative. If a FETCH
plan already holds a reader lease, real retention or compaction performs no
catalog or file mutation and returns `SKIPPED_READERS`. If maintenance has
entered deletion/replacement quiescence first, a new plan waits until catalog
publication and physical cleanup finish.

继续以 V2.1 reader-quiescence 契约为准。若 FETCH 计划已持有读租约，真实
retention 或 compaction 不修改 catalog 或文件，并返回 `SKIPPED_READERS`。若维护
先进入删除/替换静默区，新计划等待 catalog 发布和物理清理完成。

The plan keeps the captured catalog and paths stable through asynchronous
transfer. A configurable transfer timeout bounds how long a slow or stalled
client can defer maintenance. Timing out closes the channel, completes queued
writes exceptionally, and releases the plan.

计划在异步传输期间保持已捕获 catalog 与路径稳定。可配置传输超时限制慢速或停滞
客户端推迟维护的时间；超时会关闭 channel，使排队写异常完成并释放计划。

## Configuration And Eligibility / 配置与启用条件

`BrokerConfig` adds:

`BrokerConfig` 新增：

- `--fetch-transfer-mode=auto|heap`, default `auto` /
  `--fetch-transfer-mode=auto|heap`，默认 `auto`；
- `--fetch-transfer-timeout-ms=30000`, required to be positive /
  `--fetch-transfer-timeout-ms=30000`，必须为正数。

`AUTO` selects sendfile only when the log implements
`TransferablePartitionLog`, the channel supports file regions, and the pipeline
does not contain TLS. `HEAP` always uses the current `PartitionLog.read` and
`ProtocolSerdes.encodeResponse` path. Empty eligible results use a header-only
response and do not create a file region.

仅当日志实现 `TransferablePartitionLog`、channel 支持 file region 且 pipeline
不包含 TLS 时，`AUTO` 才选择 sendfile。`HEAP` 始终使用当前
`PartitionLog.read` 与 `ProtocolSerdes.encodeResponse` 路径。符合条件的空结果仅
发送响应头，不创建 file region。

## Fallback And Error Handling / 回退与错误处理

Fallback is allowed only before any response bytes are written and only for an
explicit heap mode or an unsupported capability: a non-transferable log,
unsupported channel/pipeline, or TLS. Each fallback reason is counted.

仅允许在尚未写出响应字节时回退，并且只针对显式 heap 模式或不支持的能力：日志不
可传输、channel/pipeline 不支持或存在 TLS。每种回退原因单独计数。

Corrupt segment/index data, a missing file while a lease is held, file-open
failure, frame overflow, and invalid metadata do not silently fall back. Before
the prefix is written, resources are released and the existing protocol error
path is used. After any part of a frame is queued, transfer failure or timeout
closes the channel because appending a heap response would leave an invalid
partial frame on the stream.

segment/index 损坏、持有租约时文件丢失、打开文件失败、帧超限和无效元数据不会
静默回退。写前缀前发生这些错误时释放资源并走现有协议错误路径；帧的任何部分入队
后发生传输失败或超时时关闭 channel，因为追加 heap 响应会在字节流中留下无效的
半帧。

All file channels are opened before the prefix is queued. All plan, channel,
future-listener, scheduled-timeout, and exception paths use one idempotent
cleanup owner to avoid leaked file handles or permanently active readers.

所有文件 channel 都在前缀入队前打开。计划、channel、future listener、定时超时
和异常路径共用一个幂等清理 owner，避免泄漏文件句柄或留下永久活跃 reader。

## Metrics / 指标

`FetchTransferMetrics` exposes an immutable snapshot with:

`FetchTransferMetrics` 暴露不可变快照，包括：

- sendfile responses and record bytes / sendfile 响应数与记录字节数；
- heap responses / heap 响应数；
- fallbacks grouped by disabled mode, unsupported log, unsupported pipeline,
  and TLS / 按禁用模式、不支持日志、不支持 pipeline 与 TLS 分组的回退数；
- transfer failures and transfer timeouts / 传输失败数与传输超时数。

Metrics are in-memory and cumulative for one Broker process. They prove which
path a benchmark or test exercised; they are not persisted and do not add a new
admin endpoint in V2.2.

指标在单个 Broker 进程内存中累积，用于证明 benchmark 或测试命中的路径；V2.2
不持久化指标，也不新增管理端点。

## Benchmark / 性能基准

`mq-demo` adds an opt-in `benchmark-fetch` command. It creates deterministic
data that rolls across multiple segments, runs equivalent heap and auto/sendfile
Broker cases after warm-up, and reports request count, transferred bytes,
MiB/s, mean latency, p50, and p95. The output also includes transfer metrics so
a result cannot be mistaken for sendfile when it actually used heap fallback.

`mq-demo` 新增可选 `benchmark-fetch` 命令。它创建会滚动出多个 segment 的确定性
数据，在预热后分别运行等价的 heap 与 auto/sendfile Broker 场景，并报告请求数、
传输字节、MiB/s、平均延迟、p50 和 p95。输出同时包含传输指标，避免把实际走 heap
回退的结果误认为 sendfile。

The benchmark has no timing assertion in normal CI. The V2.2 test report records
the environment, parameters, both path results, and whether sendfile improved
throughput or tail latency on the measured workload.

普通 CI 不包含时间断言。V2.2 测试报告记录环境、参数、两条路径结果，以及 sendfile
是否在实测 workload 上改善吞吐或尾延迟。

## Test Strategy / 测试策略

Storage tests prove:

存储测试验证：

- plan bytes equal current heap-read record bytes for one and multiple segments /
  单 segment 与跨 segment 下，计划字节和当前 heap 读取记录字节一致；
- sparse-index floor positioning, exact budgets, first-record-over-budget,
  empty results, and active-segment bounds / 稀疏索引 floor 定位、精确预算、首条
  超预算、空结果和 active segment 边界；
- compaction holes and offsets older than the retained `logStartOffset` /
  compaction 空洞和早于 retention 后 `logStartOffset` 的 offset；
- appends beyond the captured high watermark are excluded /
  排除捕获 high watermark 之后的 append；
- retention reports `SKIPPED_READERS` while a plan is open and proceeds after
  it closes / 计划打开时 retention 返回 `SKIPPED_READERS`，关闭后可继续；
- idempotent close and cleanup on scanner errors / 幂等关闭与扫描错误清理。

Protocol tests concatenate an encoded prefix with real segment bytes, decode it
with the existing client decoder, and compare it byte-for-byte with the heap
encoding. They also cover empty responses, multiple regions, the maximum frame,
and frame overflow.

协议测试把编码前缀与真实 segment 字节拼接，用现有客户端 decoder 解码，并与 heap
编码逐字节比较；同时覆盖空响应、多 region、最大帧和帧超限。

Broker tests prove AUTO ordering (`ByteBuf` followed by file regions), HEAP
behavior, fallback selection and metrics, cleanup after completion/failure/
timeout/channel close, real loopback TCP decoding across rolled segments, and
concurrent retention safety during an in-flight FETCH.

Broker 测试验证 AUTO 输出顺序（`ByteBuf` 后跟 file region）、HEAP 行为、回退选择
与指标、完成/失败/超时/channel 关闭后的清理、跨滚动 segment 的真实 loopback TCP
解码，以及 FETCH 在途期间的并发 retention 安全性。

Final verification runs focused storage, protocol, broker, and demo tests,
executes the benchmark, and then runs the full reactor `mvn clean verify` with
the existing 90 percent JaCoCo line-coverage gate.

最终验证运行聚焦的 storage、protocol、broker 和 demo 测试，执行 benchmark，再运行
完整 reactor `mvn clean verify`，继续满足现有 JaCoCo 90% 行覆盖率门槛。

## Acceptance Criteria / 验收标准

1. All project versions and examples resolve to `2.2.0-SNAPSHOT`.
   所有项目版本与示例均解析为 `2.2.0-SNAPSHOT`。
2. Eligible segmented FETCH requests in AUTO mode produce a prefix plus one or
   more file regions without allocating key/value payload arrays in the Broker.
   AUTO 模式下符合条件的分段 FETCH 产生前缀和一个或多个 file region，Broker 不为
   key/value payload 分配数组。
3. Heap and sendfile responses decode to identical protocol records for the
   supported boundaries.
   在支持的边界内，heap 与 sendfile 响应解码为完全相同的协议记录。
4. Sparse-index positioning, cross-segment reads, retention, compaction holes,
   and the existing max-byte semantics remain correct.
   稀疏索引定位、跨 segment 读取、retention、compaction 空洞和现有 max-byte 语义
   保持正确。
5. No success, failure, timeout, fallback, or channel-close path leaks a file
   handle or reader lease.
   成功、失败、超时、回退和 channel 关闭路径均不泄漏文件句柄或读租约。
6. Metrics prove which transfer path and fallback reason were exercised.
   指标可证明实际命中的传输路径与回退原因。
7. The benchmark records reproducible heap and sendfile results without adding
   a flaky CI timing threshold.
   benchmark 记录可重复的 heap 与 sendfile 结果，且不增加易抖动的 CI 时间门槛。
8. The full Maven reactor passes the existing verification and coverage gates.
   完整 Maven reactor 通过现有验证与覆盖率门槛。
