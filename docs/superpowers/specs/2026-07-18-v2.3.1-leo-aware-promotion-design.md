# V2.3.1 LEO-Aware Promotion Design / V2.3.1 LEO 感知 Leader 提升设计

**Status / 状态：** Approved for implementation planning / 已批准进入实施规划  
**Scope / 范围：** `R3-P1-06` and `R3-P1-07`

## 1. Goal / 目标

Persist or rebuild follower log-end offsets (LEO) in a Controller-visible place, then use those offsets during manual leader failover so the promoted leader is the safest available ISR member.

将 follower 日志末端位点（LEO）持久化或重建到 Controller 可见的位置，并在手动 Leader 故障转移时使用这些位点，使被提升的 Leader 是当前 ISR 中最安全的候选者。

## 2. Problem / 问题

`ReplicaStateManager` currently keeps follower LEO in broker-local memory. That helps a running leader compute replication high watermark, but it does not survive broker restart and it is not visible to `ClusterController.markBrokerOffline` when the Controller elects a new leader.

`ReplicaStateManager` 目前把 follower LEO 保存在 Broker 本地内存中。这能帮助运行中的 Leader 计算 replication high watermark，但 Broker 重启后会丢失，而且 `ClusterController.markBrokerOffline` 在 Controller 选举新 Leader 时看不到这些数据。

Because of that, R3-P1-06 and R3-P1-07 should be solved together. Persisting only the local `ReplicaStateManager` would not give Controller enough information for LEO-aware promotion.

因此，R3-P1-06 与 R3-P1-07 应一起解决。只持久化本地 `ReplicaStateManager` 不能给 Controller 提供 LEO 感知提升所需的信息。

## 3. Chosen Approach / 选定方案

Add Controller-visible replica LEO state to cluster metadata.

在集群元数据中增加 Controller 可见的副本 LEO 状态。

Each `ClusterMetadata.PartitionEntry` gains a `Map<Integer, Long> replicaLogEndOffsets`, keyed by broker ID. The map records the latest known LEO for the partition replica on each broker.

每个 `ClusterMetadata.PartitionEntry` 新增 `Map<Integer, Long> replicaLogEndOffsets`，以 Broker ID 为 key，记录该分区副本在各 Broker 上的最新已知 LEO。

The Controller remains the source of truth for this metadata. Followers learn it through existing metadata sync. This is intentionally a small metadata extension, not a new protocol family or distributed lease system.

Controller 继续作为该元数据的事实来源。Follower 通过现有元数据同步获取它。这是一个小型元数据扩展，不引入新的协议族或分布式 lease 系统。

## 4. LEO Update Semantics / LEO 更新语义

LEO updates must be monotonic:

1. Reject negative LEO values.
2. Ignore stale updates that are lower than the stored value.
3. Accept equal or higher values.
4. Keep entries for all known replicas until topic metadata changes; this design does not implement ISR shrink/expand.

LEO 更新必须单调：

1. 拒绝负数 LEO。
2. 忽略低于已存值的过期更新。
3. 接受相等或更高值。
4. 保留所有已知副本的条目直到 Topic 元数据变化；本设计不实现 ISR 收缩/扩容。

Leader-side update points:

- After `PRODUCE`, the leader updates its own broker ID to the local partition high watermark.
- After serving `REPLICA_FETCH`, the leader updates the requesting follower broker ID to `fetchOffset + fetchedRecordCount`.
- On leadership note/transition, the promoted leader updates its own broker ID to its local high watermark.

Leader 侧更新点：

- `PRODUCE` 后，Leader 将自身 Broker ID 更新为本地分区 high watermark。
- 响应 `REPLICA_FETCH` 后，Leader 将请求方 follower Broker ID 更新为 `fetchOffset + fetchedRecordCount`。
- 记录/切换领导权时，被提升的 Leader 将自身 Broker ID 更新为本地 high watermark。

## 5. Metadata Sync / 元数据同步

`ProtocolMessages.PartitionMetadata` and protocol serde should carry `replicaLogEndOffsets` in metadata responses. For compatibility inside this development line, the map is appended after ISR broker IDs in the metadata partition encoding.

`ProtocolMessages.PartitionMetadata` 与协议编解码需要在 metadata response 中携带 `replicaLogEndOffsets`。在当前开发线内，为保持结构清晰，该 map 追加在 metadata 分区编码中的 ISR broker IDs 之后。

`MetadataSync.applyMetadata` copies the map into follower-local `ClusterController` snapshots. This lets non-controller brokers route and reason from the same Controller-visible LEO view after sync.

`MetadataSync.applyMetadata` 将该 map 复制到 follower 本地 `ClusterController` 快照中。这样非 Controller Broker 在同步后也能基于同一份 Controller 可见 LEO 视图进行路由和判断。

## 6. Election Semantics / 选举语义

When `markBrokerOffline` needs a replacement leader:

1. Candidate must be online.
2. Candidate must remain in ISR.
3. Candidate must not be the offline broker.
4. Select the candidate with the highest known LEO.
5. If multiple candidates have the same known LEO, choose the earliest candidate by configured `replicaBrokerIds` order.
6. If a candidate has no stored LEO, treat it as `0` for comparison.
7. If no candidate exists, return `INVALID_REQUEST` and mutate nothing.

当 `markBrokerOffline` 需要替代 Leader 时：

1. 候选 Broker 必须在线。
2. 候选 Broker 必须仍在 ISR 中。
3. 候选 Broker 不能是待离线 Broker。
4. 选择已知 LEO 最大的候选者。
5. 多个候选者 LEO 相同时，按配置的 `replicaBrokerIds` 顺序选择最靠前者。
6. 候选者没有已存 LEO 时，按 `0` 参与比较。
7. 如果不存在候选者，返回 `INVALID_REQUEST` 且不修改任何元数据。

This preserves the R3-P1-01 preferred-order rule as a tie-breaker while adding R3-P1-07 safety ordering.

这保留 R3-P1-01 的 preferred 顺序作为平局规则，同时增加 R3-P1-07 的安全排序。

## 7. Persistence and Recovery / 持久化与恢复

Because `replicaLogEndOffsets` lives in `ClusterMetadata`, `MetadataStore.save` persists it in `cluster-metadata.json`. On Controller restart, `MetadataStore.load` restores the map with the rest of topic metadata.

因为 `replicaLogEndOffsets` 位于 `ClusterMetadata` 中，`MetadataStore.save` 会将其持久化到 `cluster-metadata.json`。Controller 重启时，`MetadataStore.load` 会与其他 Topic 元数据一起恢复该 map。

Metadata validation should reject negative LEO values and tolerate missing maps from older metadata files by normalizing them to empty maps.

元数据校验应拒绝负数 LEO，并允许旧元数据文件缺少该 map，通过 normalize 补成空 map。

## 8. Out of Scope / 不在范围内

This design does not implement:

- Lag-based ISR shrink/expand (`R3-P1-02`).
- Sendfile concurrency or failure handling (`R3-P1-03`, `R3-P1-04`).
- Replica-fetch connection pooling (`R3-P1-05`).
- Dedicated `ReplicaFetcher`, `LeaderReplicaClient`, or handler-path coverage beyond what this feature requires (`R3-P1-08`).
- Automatic broker failure detection, fencing, epochs, or Controller HA.

本设计不实现：

- 基于滞后的 ISR 收缩/扩容（`R3-P1-02`）。
- sendfile 并发或失败处理（`R3-P1-03`、`R3-P1-04`）。
- 副本拉取连接池（`R3-P1-05`）。
- 除本功能所需之外的 `ReplicaFetcher`、`LeaderReplicaClient` 或 handler 路径专项覆盖（`R3-P1-08`）。
- 自动 Broker 故障检测、fencing、epoch 或 Controller 高可用。

## 9. Test Strategy / 测试策略

Use TDD with focused tests first:

1. `ClusterControllerTest` should prove `markBrokerOffline` promotes the ISR candidate with the highest LEO even when that candidate is later in `replicaBrokerIds` order.
2. `ClusterControllerTest` should prove equal LEO falls back to `replicaBrokerIds` order.
3. `ClusterControllerTest` should prove stale lower LEO updates do not reduce stored LEO.
4. `MetadataStoreTest` should prove `replicaLogEndOffsets` round-trips through `cluster-metadata.json` and negative values are rejected.
5. `ProtocolSerdesTest` should prove metadata responses preserve the LEO map.
6. A handler or integration test should prove `PRODUCE` and `REPLICA_FETCH` update metadata LEO values.
7. Full verification must pass with `mvn clean verify -gs .mvn/settings.xml -s .mvn/settings.xml`.

先用聚焦测试进行 TDD：

1. `ClusterControllerTest` 证明即使候选者在 `replicaBrokerIds` 顺序中更靠后，`markBrokerOffline` 也会提升 LEO 最高的 ISR 候选者。
2. `ClusterControllerTest` 证明 LEO 相同时回退到 `replicaBrokerIds` 顺序。
3. `ClusterControllerTest` 证明更低的过期 LEO 更新不会降低已存 LEO。
4. `MetadataStoreTest` 证明 `replicaLogEndOffsets` 能在 `cluster-metadata.json` 中往返保存，并拒绝负数值。
5. `ProtocolSerdesTest` 证明 metadata response 会保留 LEO map。
6. handler 或集成测试证明 `PRODUCE` 与 `REPLICA_FETCH` 会更新 metadata LEO 值。
7. 最终必须通过 `mvn clean verify -gs .mvn/settings.xml -s .mvn/settings.xml`。

## 11. Completion Criteria / 完成标准

The work is complete when metadata stores replica LEO durably, metadata sync propagates it, leader promotion uses highest known LEO with preferred-order tie-break, stale LEO updates cannot regress state, focused tests prove each behavior, and full Maven verification passes.

当元数据能持久保存 replica LEO、元数据同步能传播它、Leader 提升按最高已知 LEO 并以 preferred 顺序打破平局、过期 LEO 更新不能回退状态、聚焦测试证明每项行为，且完整 Maven 验证通过时，本项工作才算完成。
