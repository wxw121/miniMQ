# MiniMQ V2.5.0 Broker 租约与自动故障转移设计

**状态：** 已确认，等待用户审阅文档
**日期：** 2026-07-19
**目标版本：** `2.5.0`
**开发分支：** `dev/v2.5.0-broker-leases-auto-failover`

## 1. Summary / 摘要

V2.4.0 已完成维护能力的运维接口闭环。当前最重要的可靠性缺口重新回到复制控制面：Broker 是否存活仍由静态 Controller 记录，Leader 故障后需要人工调用 `MARK_BROKER_OFFLINE`，与 Controller 失联的旧 Leader 也可能继续接受请求。

V2.5.0 在不引入 etcd、ZooKeeper 或 Controller 选举的前提下，增加 Broker 心跳租约、自动过期下线、LEO 感知 Leader 故障转移和 Broker 自我 fencing。目标是让旧 Leader 在 Controller 选出新 Leader 之前停止服务，并让已追平的 ISR 自动接管分区。

## 2. Chosen Approach / 选定方案

采用“静态 Controller 租约 + Broker 自我 fencing”：

1. 每个 Broker 定期向静态 Controller 续租。
2. Broker 使用本机单调时钟判断续租是否超时，并在 Controller 租约过期前自我 fencing。
3. Controller 使用独立租约监控器扫描过期 Broker，原子复用现有下线、ISR 更新和 LEO 感知选主逻辑。
4. Broker 恢复后必须重新注册、同步完整元数据并确认角色，不能仅凭一次心跳直接解封。
5. 每次被 Controller 接受的新进程注册都会获得单调递增的 `brokerEpoch`，过期 epoch 不能续租。

该方案比完整的数据面 `leaderEpoch` 改造范围小，且不增加外部服务依赖。数据面 `leaderEpoch` 和外部协调服务分别留给后续加固和 V3.0。

## 3. Alternatives Considered / 备选方案

### 3.1 租约加数据面 Leader Epoch

在租约基础上，把 `leaderEpoch` 加入元数据以及 PRODUCE/FETCH 请求。它能帮助新 Leader 拒绝过期客户端，但不能单独让隔离中的旧 Leader 获知自己已失效，因此仍需要自我 fencing。该方案会扩大协议、客户端和数据面改动，本版本暂不采用。

### 3.2 直接引入 etcd 或 ZooKeeper

外部协调后端可以同时提供 Broker lease、Controller 选举和原子 epoch，但会引入部署依赖、外部故障模型和完整控制面重构。该范围属于 V3.0，不纳入 V2.5.0。

## 4. Scope / 范围

### 4.1 Included / 包含

- Broker 心跳与 Controller 租约续期。
- Broker 自我 fencing 和恢复状态机。
- 持久化的 `brokerEpoch`。
- Controller 自动过期下线和 LEO 感知选主。
- Follower 过期后的 ISR 收缩。
- 无可用 ISR 时的安全冻结，不执行非同步副本提升。
- Producer/Consumer 对 `BROKER_FENCED` 的一次元数据刷新重试。
- 可控时钟单测以及真实 TCP 自动故障转移集成测试。
- 版本、架构、设计、路线图、测试文档和测试报告同步。

### 4.2 Excluded / 不包含

- etcd、ZooKeeper、Controller 选举或 Controller HA。
- 客户端请求携带 `leaderEpoch`。
- 非同步副本强制提升或数据丢失式恢复。
- Producer acknowledgement 新策略。
- TLS、Broker 心跳鉴权和滚动混合版本升级。
- 熔断、限流、全面运行指标和自适应故障检测器。

## 5. Architecture / 架构

### 5.1 BrokerLeaseService

`BrokerLeaseService` 运行在每个 Broker 上，拥有一个单线程调度器和一个可复用的 Controller 连接。它负责注册、续租、记录最后成功续租的单调时钟时间、触发本地 fencing，并在连接失败后关闭旧连接再重连。

服务关闭时必须停止调度器并关闭 Controller 连接。心跳及重连不得运行在 Netty EventLoop 上。

### 5.2 BrokerLeaseMonitor

`BrokerLeaseMonitor` 仅运行在 Controller Broker 上。它维护 Broker 当前 epoch 对应的内存租约截止时间，定期收集过期项，并通过 `ClusterController.expireBrokerLease(brokerId, expectedEpoch)` 执行原子状态变更。

租约扫描不能直接修改 `ClusterMetadata`，所有变更仍由 `ClusterController` 的同步边界完成并通过 `MetadataStore` 持久化。

### 5.3 BrokerAvailabilityGuard

`BrokerAvailabilityGuard` 保存 Broker 当前状态，并为请求处理、`ReplicaFetcher`、`ReplicaLeoReporter` 和维护执行提供统一判断。它不能在各调用点复制不同的 fencing 规则。

Fenced Broker 必须拒绝：

- `PRODUCE`
- 客户端 `FETCH`
- `REPLICA_FETCH`
- 真实 `MAINTENANCE_RUN`

Fenced Broker 仍允许维护预览和维护指标查询，因为这两个操作不修改存储。

## 6. Broker State Model / Broker 状态模型

```text
STARTING -> ACTIVE -> FENCED -> RECOVERING -> ACTIVE
```

| 状态 | 进入条件 | 允许行为 |
| --- | --- | --- |
| `STARTING` | Broker 进程启动，尚未完成注册和元数据同步 | 仅执行启动注册与同步，不开放数据面 |
| `ACTIVE` | 已获得有效 epoch，元数据同步完成，租约有效 | 正常读写、复制和维护 |
| `FENCED` | 自我 fencing 超时、Controller 返回过期 epoch，或租约服务显式失败 | 拒绝数据面和真实维护，暂停副本拉取与 LEO 上报 |
| `RECOVERING` | Fenced Broker 已重新连接 Controller | 重新注册、同步元数据和恢复角色，仍拒绝数据面 |

所有状态转换必须原子可见。`ACTIVE` 只能在注册、完整元数据同步和租约建立全部成功后进入。

## 7. Timing And Configuration / 时序与配置

新增 Broker 配置：

```text
--broker-heartbeat-interval-ms       默认 1000
--broker-self-fence-timeout-ms       默认 3000
--controller-broker-lease-timeout-ms 默认 5000
```

启动时必须满足：

```text
heartbeat interval < self-fence timeout < controller lease timeout
```

所有值必须为正数。Controller 在注册响应中返回实际租约时间；Broker 如果发现自己的 fencing 超时不小于 Controller 租约，则保持 `STARTING` 并终止启动。

Broker 和 Controller 的运行时超时判断使用 `System.nanoTime()` 等单调时钟。持久化元数据不保存单调时钟值。

Broker 将一次成功续租锚定到该心跳请求的本地发送时刻，而不是响应接收时刻。这样即使响应传输延迟较高，本地 self-fence 截止时间也不会被延后到 Controller 租约截止时间之后。

## 8. Protocol And Errors / 协议与错误码

新增 API：

```text
16 BROKER_HEARTBEAT
```

消息定义：

```java
RegisterBrokerResponse(long brokerEpoch, long leaseTimeoutMs)

BrokerHeartbeatRequest(int brokerId, long brokerEpoch)

BrokerHeartbeatResponse()
```

新增错误码：

```text
BROKER_FENCED
BROKER_ID_IN_USE
```

`BROKER_ID_IN_USE` 是设计自审后补充的安全约束：如果相同 `brokerId` 的旧 epoch 仍持有有效租约，Controller 不接受第二个进程注册。新进程必须等待旧租约过期，避免 Controller 切换 epoch 后旧进程在下一次心跳前仍短暂处于 ACTIVE 状态。

现有 PRODUCE/FETCH 消息格式不变。V2.5.0 不支持新旧 Broker 混合部署，但普通 Producer/Consumer 的数据体格式保持兼容。

## 9. Metadata And Lease Persistence / 元数据与租约持久化

`ClusterMetadata.BrokerEntry` 增加：

```java
long brokerEpoch;
```

`ClusterMetadata.PartitionEntry` 增加：

```java
boolean frozen;
```

`frozen` 用于区分“尚未归一化的空 ISR”和“因没有可用 ISR 而主动冻结的分区”。冻结分区允许 `isrBrokerIds` 为空，元数据归一化不能自动把离线 Leader 补回 ISR。

epoch 在每次被接受的新进程注册时递增并随集群元数据原子保存。租约截止时间仅存在于 Controller 内存，不写入 JSON。

Controller 重启后，为持久化为在线的 Broker 建立一个完整租约周期的恢复宽限期。宽限期内，匹配持久化 epoch 的心跳可以恢复续租。宽限期结束仍未续租的 Broker 按正常过期流程处理。

同一 `brokerId` 的注册规则：

1. 不存在 Broker：创建 epoch `1` 并建立租约。
2. Broker 存在但租约已过期：epoch 加一，更新地址并建立新租约。
3. Broker 存在且当前租约有效：返回 `BROKER_ID_IN_USE`，不修改 epoch 或元数据。

## 10. Normal Data Flow / 正常数据流

```text
Broker STARTING
  -> REGISTER_BROKER
  -> Controller 返回 brokerEpoch 和 leaseTimeout
  -> Broker 拉取并应用完整元数据
  -> Broker 建立本地租约计时
  -> Broker ACTIVE
  -> 周期性 BROKER_HEARTBEAT
  -> Controller 仅在 brokerId 和 brokerEpoch 匹配时续租
```

Controller Broker 也使用同一租约语义，但可以通过本地调用续租，不需要连接自身监听端口。

## 11. Failure Handling / 故障处理

### 11.1 Follower Lease Expiry

Follower 过期时，Controller 将其标记离线并从相关 ISR 中移除，不改变 Leader。Follower 恢复后先作为普通在线副本追赶；只有现有 LEO 调节逻辑确认其达到容忍范围后，才重新进入 ISR。

### 11.2 Leader Lease Expiry With Eligible ISR

Controller 在同一个同步元数据事务中：

1. 校验当前 epoch 仍等于扫描得到的 `expectedEpoch`。
2. 标记旧 Broker 离线。
3. 将旧 Broker 移出 ISR。
4. 从在线 ISR 中选择持久化 LEO 最高的副本，以配置副本顺序作为平局规则。
5. 更新 Leader 并保存一次元数据。

任一分区无法完成预校验时，不得留下部分应用的元数据。

### 11.3 Leader Lease Expiry Without Eligible ISR

Controller 不执行非同步副本提升。Broker 被标记离线，相关分区保留原 Leader 归属作为冻结恢复点，但该 Leader 不出现在在线 Broker 列表中，因此客户端无法路由请求。

冻结时设置 `frozen = true`、清空 ISR，并保留原 `leaderBrokerId` 作为唯一恢复归属。只有该原 Leader 使用同一 `brokerId` 重新注册时，Controller 才将它加入 ISR、设置 `frozen = false` 并恢复分区。其他副本恢复不能自动解除冻结。

这是一项显式的安全优先取舍：分区保持不可用，直到原 Broker 使用原 `brokerId` 和数据目录恢复并重新注册。本版本不尝试从未知进度副本恢复。

### 11.4 Controller Failure Or Network Partition

Broker 从最后一次成功续租开始计算本地超时。在 `brokerSelfFenceTimeoutMs` 到达时进入 `FENCED`，停止数据面、真实维护、副本拉取和 LEO 上报。Controller 只有在更晚的 `controllerBrokerLeaseTimeoutMs` 到达后才执行故障转移，因此旧 Leader 先停止服务，新 Leader 后接管。

### 11.5 Broker Recovery

```text
FENCED
  -> RECOVERING
  -> 等待旧租约过期
  -> REGISTER_BROKER 获得新 epoch
  -> 同步完整元数据
  -> 恢复 ReplicaFetcher 和 LEO 上报
  -> ACTIVE
```

一次成功心跳不能直接把 `FENCED` 转换为 `ACTIVE`。

## 12. Client Behavior / 客户端行为

Producer 和 Consumer 把 `BROKER_FENCED` 视为元数据过期信号，复用当前 `NOT_LEADER` 路径：失效 Topic 元数据，刷新一次并重试一次。重试预算耗尽后抛出带 Topic、分区和 Broker 上下文的类型化客户端异常。

`BROKER_FENCED` 不允许无限重试，也不进入连接级固定退避循环。

## 13. Concurrency And Atomicity / 并发与原子性

- `ClusterController` 的注册、心跳、租约过期、ISR 更新和 Leader 选举继续使用同一个同步边界。
- `expireBrokerLease(brokerId, expectedEpoch)` 只有在当前 epoch 匹配时才能提交。
- 租约扫描先收集候选，再逐个调用 Controller；扫描器不持有元数据内部引用。
- Controller 持久化失败时，本次过期变更整体失败并记录错误，不能只更新内存状态。
- Broker 状态转换必须先进入 `FENCED`，再暂停后台复制组件；请求守卫以状态为最终准入依据，避免暂停过程中的竞态。

## 14. Test Strategy / 测试策略

### 14.1 Protocol And Configuration

- `ProtocolSerdesTest` 覆盖注册响应、心跳消息和新增错误码。
- `BrokerConfigTest` 覆盖默认值、参数解析、非正数和三段时间顺序校验。

### 14.2 Lease Units

- `BrokerLeaseServiceTest` 覆盖正常续租、连接复用、连续失败 fencing、过期 epoch、重复 Broker ID、恢复注册和资源关闭。
- `BrokerLeaseMonitorTest` 使用可控单调时钟覆盖续租、过期扫描、Controller 重启宽限期和 epoch 竞态。
- `BrokerAvailabilityGuardTest` 覆盖全部状态和准入规则。

### 14.3 Controller And Handler

- `ClusterControllerTest` 覆盖 Follower 过期、Leader 自动选举、最高 LEO 选择、无 ISR 冻结、旧 epoch 拒绝和注册/过期并发。
- `EmbeddedBrokerChannelTest` 覆盖 Fenced Broker 对数据面和维护 API 的响应。

### 14.4 Integration

- `ReplicationIntegrationTest` 使用短测试租约启动三个真实 Broker。
- 写入并等待两个 Follower 确认 LEO 后停止 Leader，验证 Controller 自动选择最高 LEO ISR。
- 验证 Producer 使用旧元数据时刷新并路由到新 Leader。
- 使用原数据目录恢复旧 Broker，验证追赶并重新进入 ISR。
- 构造无可用 ISR 场景，验证分区冻结且未确认数据不可见。

租约单测不得依赖真实 `sleep(5s)`；使用可控时钟和显式调度。真实 TCP 集成测试必须有明确截止时间和失败信息，不能无限轮询。

## 17. Open Risks / 已接受或延后的风险

- 静态 Controller 仍是控制面单点，Controller HA 延后到 V3.0。
- 本版本依赖 Broker ID 与数据目录身份连续性；尚未引入独立磁盘身份或存储 UUID。
- 固定超时可能在高延迟网络中产生误 fencing；自适应 failure detector 延后。
- 不支持混合版本滚动升级，升级时需要停止整个测试集群。
- 没有数据面 `leaderEpoch`；本版本通过“Broker 先自我 fencing、Controller 后选主”的时间顺序保证旧 Leader 不继续服务。
