# MiniMQ V2.1.2 Maintenance Observability Design / MiniMQ V2.1.2 维护可观测性设计

**Status / 状态：** Approved for implementation by the requested V2.1 hardening sequence / 已按要求的 V2.1 加固顺序批准实施

**Goal:** Make retention and compaction observable and bounded before moving the
V2.1 storage line to read-performance work.

**目标：** 在 V2.1 存储线进入读取性能工作之前，使保留和压缩具备可观测性并受到明确限制。

## Scope / 范围

V2.1.2 adds three storage-maintenance capabilities in this order:

V2.1.2 按以下顺序增加三项存储维护能力：

1. A dry-run report that lists the partition, action, segment base offset,
   original log bytes, and affected first/last offsets without changing files,
   catalogs, checkpoints, or logical records.
   dry-run 报告列出分区、动作、segment base offset、原始日志字节数，以及受影响的首尾 offset，但不更改文件、目录、检查点或逻辑记录。
2. In-memory cumulative metrics for actual deleted bytes/segments, compacted
   bytes/segments, maintenance skipped because readers are active, cleanup
   failures, and the last real maintenance status.
   提供内存累计指标，包括实际删除的字节数/segment 数、压缩的字节数/segment 数、因 reader 活跃而跳过维护的次数、清理失败次数，以及上一次真实维护状态。
3. Compaction limits by original segment bytes and segment count, an optional
   UTC maintenance window for append-triggered runs, and public Java entrypoints
   for manual execution, dry-run, and metric snapshots.
   按原始 segment 字节数和 segment 数限制压缩；支持可选的 UTC 维护窗口；并提供用于手动执行、dry-run 和获取指标快照的公共 Java 入口。

The broker protocol, an HTTP/admin endpoint, a user-facing CLI maintenance
command, persistent metrics, and asynchronous scheduling are excluded. The
broker-facing manual boundary is `PartitionManager`; a later operator API can
render its report and metric types without reaching into storage internals.

不包含 broker 协议、HTTP/admin 端点、面向用户的 CLI 维护命令、持久化指标和异步调度。面向 broker 的手动调用边界为 `PartitionManager`；后续运维 API 可以呈现其报告和指标类型，而无需访问存储内部实现。

## Alternatives Considered / 备选方案

1. **Chosen: extend the existing serialized maintenance path.** Reuse the
   retention and compaction planners, expose immutable reports, and keep the
   current append-triggered lifecycle. This has the smallest behavioral surface
   and preserves the V2.1.1 recovery model.
   **选定方案：扩展现有串行维护路径。** 复用保留与压缩 planner，公开不可变报告，并保留当前由 append 触发的生命周期。该方案行为影响面最小，并保持 V2.1.1 恢复模型不变。
2. Add a broker admin protocol and CLI now. This would make the controls directly
   operator-facing, but it adds protocol compatibility, authorization, and
   integration-test work outside the storage-hardening scope.
   立即增加 broker admin 协议和 CLI。这样可直接向运维人员提供控制能力，但会引入协议兼容性、授权和集成测试工作，超出本次存储加固范围。
3. Add a background maintenance executor. This would remove work from the append
   call, but introduces shutdown, queueing, overlap, and failure-propagation
   semantics that are not needed to satisfy the requested limits and window.
   增加后台维护 executor。这样可将工作移出 append 调用，但会引入关闭、排队、重叠和故障传播语义，而满足当前限额与窗口需求并不需要这些复杂性。

## Architecture / 架构

`LogManager` remains the maintenance coordinator. It exposes
`dryRunMaintenance()`, `maintain()`, and `maintenanceMetrics()`. `PartitionManager`
forwards those methods as the broker module boundary. Reports and metrics are
immutable records in `mq-storage`.

`LogManager` 继续作为维护协调器，对外提供 `dryRunMaintenance()`、`maintain()` 和 `maintenanceMetrics()`。`PartitionManager` 将这些方法转发为 broker 模块边界。报告和指标采用 `mq-storage` 中的不可变 record。

Each partition uses one planning order for both preview and execution:

每个分区的预览与执行共用同一规划顺序：

```text
current sealed segments
  -> plan retention deletions
  -> remove those segments from the simulated catalog
  -> plan compaction over the surviving segments
  -> produce ordered segment actions
```

Dry-run stops after planning. Execution applies retention and then compaction,
publishes the same action semantics, and saves a checkpoint after a successful
or no-op run. Reports are sorted by partition and segment base offset so repeated
previews over unchanged storage are stable.

dry-run 在规划完成后停止。真实执行先应用保留，再应用压缩；发布相同的动作语义，并在成功或无操作运行后保存检查点。报告按分区和 segment base offset 排序，因此对未变更存储的重复预览结果保持稳定。

## Reader Safety / Reader 安全

A real partition maintenance pass attempts to enter reader quiescence without
waiting and before compaction planning scans segment contents. If any read
snapshot is active, it performs no catalog or file mutation and returns
`SKIPPED_READERS`. `skippedDueToReaders` counts maintenance attempts deferred by
active readers. Dry-run remains available while readers are active because it
only reads immutable sealed segments.

真实分区维护会在压缩规划扫描 segment 内容之前尝试进入 reader 静默状态，且不会等待。如果存在活动读快照，则不修改任何目录或文件，并返回 `SKIPPED_READERS`。`skippedDueToReaders` 统计因活动 reader 而推迟的维护尝试次数。dry-run 在 reader 活跃时仍可执行，因为它只读取不可变的已封闭 segment。

Once a pass acquires quiescence, new reads wait until catalog publication and
physical replacement/deletion finish. The existing compaction byte/segment
budgets bound that interval. This preserves the V2.1.1 snapshot contract while
preventing maintenance from waiting indefinitely on fetch traffic.

维护一旦取得静默状态，新读取就会等待，直到目录发布以及物理替换/删除完成。现有压缩字节/segment 预算会限制该区间。这样既保持 V2.1.1 的快照契约，也防止维护无限期等待 fetch 流量。

## Status And Metric Semantics / 状态与指标语义

`MaintenanceStatus` values have these meanings:

`MaintenanceStatus` 各值含义如下：

| Status / 状态 | Meaning / 含义 |
| --- | --- |
| `NEVER_RUN` | No real maintenance attempt has occurred. / 尚未发生真实维护尝试。 |
| `SUCCESS` | At least one planned action was executed. / 至少执行了一个已规划动作。 |
| `NOOP` | Maintenance was enabled but no action was eligible. / 维护已启用，但没有符合条件的动作。 |
| `SKIPPED_DISABLED` | A manual call found all policies disabled. / 手动调用发现所有策略均已禁用。 |
| `SKIPPED_WINDOW` | An append cadence was due outside the configured UTC window. / append 调度到期，但当前时间不在配置的 UTC 窗口内。 |
| `SKIPPED_READERS` | Eligible actions were not executed because a reader snapshot was active. / 因存在活动读快照，符合条件的动作未执行。 |
| `FAILED` | A real maintenance attempt raised during planning, publication, replacement, deletion, or checkpointing. / 真实维护尝试在规划、发布、替换、删除或写检查点期间抛出异常。 |

`runs` counts real enabled maintenance attempts, including no-op and reader-skip
attempts. `dryRuns` counts previews separately. Dry-run reports have their own
status but do not overwrite `lastRunStatus`. Deleted and compacted counters only
include actions that actually completed. `cleanupFailures` increments once for
each failed real maintenance attempt.

`runs` 统计已启用的真实维护尝试，包括无操作和 reader 跳过。`dryRuns` 单独统计预览次数。dry-run 报告具有自己的状态，但不会覆盖 `lastRunStatus`。删除和压缩计数器只包含实际完成的动作。每次真实维护尝试失败，`cleanupFailures` 增加一次。

## Controls / 控制项

`CompactionPolicy.maxSegmentsPerRun` limits the oldest contiguous sealed segment
prefix. `maxBytesPerRun == 0` means unlimited bytes; otherwise adding a segment
that would exceed the budget stops selection. A segment larger than the budget
is deferred rather than partially rewritten.

`CompactionPolicy.maxSegmentsPerRun` 限制最旧的连续已封闭 segment 前缀。`maxBytesPerRun == 0` 表示字节数不限；否则，当加入某个 segment 会超过预算时停止选择。大于预算的单个 segment 会被推迟，不会只重写其中一部分。

The maintenance window is expressed as UTC start-inclusive/end-exclusive hours.
Equal start and end means all day; `-1/-1` disables the window. Only append-
triggered maintenance checks the window. Manual `maintain()` bypasses it so an
operator-controlled invocation can run at any time, while still respecting
reader safety and compaction budgets.

维护窗口使用 UTC 小时表示，开始时间包含、结束时间不包含。开始与结束相同表示全天；`-1/-1` 表示禁用窗口。只有 append 触发的维护会检查窗口。手动 `maintain()` 会绕过窗口，因此由运维人员控制的调用可以随时运行，但仍须遵守 reader 安全和压缩预算。

## Error Handling / 错误处理

- Invalid byte/segment budgets and partial or out-of-range windows fail during
  configuration construction.
  无效的字节/segment 预算，以及不完整或超出范围的窗口，会在构造配置时失败。
- A failed real pass records `FAILED` and one cleanup failure before propagating
  the original exception.
  真实维护失败时，先记录 `FAILED` 和一次清理失败，再传播原始异常。
- Dry-run propagates planning/read errors but never increments actual deletion,
  compaction, or cleanup counters.
  dry-run 会传播规划/读取错误，但绝不增加实际删除、压缩或清理计数器。
- Existing catalog recovery remains authoritative for interrupted cleaned and
  obsolete artifacts.
  对中断后遗留的 cleaned 和 obsolete 工件，仍以现有目录恢复机制为权威。

## Test Strategy / 测试策略

- Prove dry-run reports retention and compaction actions, bytes, and offset
  ranges without changing records or files.
  验证 dry-run 能报告保留与压缩动作、字节数和 offset 范围，同时不更改记录或文件。
- Prove dry-run compaction is planned after simulated retention, so one segment
  is not reported for an action that execution would never perform.
  验证 dry-run 在模拟保留之后规划压缩，确保不会把真实执行绝不会处理的 segment 报告为动作对象。
- Hold a real read snapshot and prove maintenance returns `SKIPPED_READERS`
  without mutation or blocking, then succeeds after the snapshot closes.
  持有真实读快照，验证维护不修改、不阻塞并返回 `SKIPPED_READERS`；随后在快照关闭后验证维护成功。
- Prove real counters change only after execution and dry-run does not replace
  `lastRunStatus`.
  验证真实计数器只在执行后变化，并且 dry-run 不会替换 `lastRunStatus`。
- Prove byte/segment caps, normal and overnight UTC windows, all-day windows,
  invalid partial windows, and manual window bypass.
  验证字节/segment 上限、普通和跨夜 UTC 窗口、全天窗口、无效的不完整窗口，以及手动调用绕过窗口。
- Run focused storage/broker tests and full Maven verification with the existing
  90 percent JaCoCo line-coverage gate.
  运行聚焦的 storage/broker 测试和完整 Maven 验证，并满足现有 90% JaCoCo 行覆盖率门槛。
