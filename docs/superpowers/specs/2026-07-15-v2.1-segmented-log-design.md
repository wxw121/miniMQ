# MiniMQ V2.1 Segmented Log Design / MiniMQ V2.1 分段日志设计

**Status / 状态：** Approved for planning / 已批准进入规划

**Goal:** Replace the single file per partition layout with recoverable segmented
logs and sparse indexes in V2.1.0, then add retention and key-based compaction
over sealed segments in V2.1.1.

**目标：** 在 V2.1.0 中，将每个分区单文件的布局替换为可恢复的分段日志和稀疏索引；随后在 V2.1.1 中，为已封闭 segment 增加保留策略和基于 key 的压缩。

## Scope And Release Split / 范围与版本拆分

| Release / 版本 | In scope / 范围内 | Explicitly excluded / 明确排除 |
| --- | --- | --- |
| V2.1.0 | Segmented partition logs, size-based roll, sparse offset indexes, catalog recovery, legacy single-file migration, WAL/checkpoint integration / 分段分区日志、按大小滚动、稀疏 offset 索引、目录恢复、旧版单文件迁移、WAL/检查点集成 | Retention deletion, compaction, replicas, service discovery, circuit breaking, Epoll, mmap, sendfile / 保留删除、压缩、副本、服务发现、熔断、Epoll、mmap、sendfile |
| V2.1.1 | Time/size retention, sealed-segment compaction, atomic catalog replacement, maintenance lifecycle / 按时间或大小保留、已封闭 segment 压缩、目录原子替换、维护生命周期 | Replication, ISR, controller election, distributed discovery, zero-copy reads / 复制、ISR、控制器选举、分布式发现、零拷贝读取 |

The V2.0 `WriteAheadLog`, `RecoveryCheckpoint`, `CheckpointStore`, and
`FlushPolicy` remain authoritative and retain their existing behavior. V2.1
changes the partition-log layout only.

V2.0 的 `WriteAheadLog`、`RecoveryCheckpoint`、`CheckpointStore` 和 `FlushPolicy` 仍是权威实现，并保留现有行为。V2.1 只更改分区日志布局。

## Alternatives Considered / 备选方案

1. Implement rolling, indexing, retention, and compaction in one release.
   This produces the full feature set quickly, but mixes hot-write, deletion,
   and rewrite failure modes before the segment format is proven.

   在一个版本中实现滚动、索引、保留和压缩。这样能快速交付完整功能集，但会在 segment 格式得到验证之前，混合热写入、删除和重写等故障模式。
2. Add segment rolling first and defer the index. This is the smallest change,
   but it leaves reads linear and does not establish the index format needed by
   compaction.

   先增加 segment 滚动，延后索引。这是改动最小的方案，但读取仍为线性扫描，也无法建立压缩所需的索引格式。
3. **Chosen:** deliver V2.1.0 as segmented logs plus sparse indexes, then
   deliver V2.1.1 as background maintenance over immutable segments. The first
   release validates the file and recovery contracts; the second operates only
   on sealed files.

   **选定方案：** V2.1.0 交付分段日志和稀疏索引，V2.1.1 再交付针对不可变 segment 的后台维护。第一个版本验证文件和恢复契约；第二个版本只操作已封闭文件。

## V2.1.0 Architecture / V2.1.0 架构

`LogManager` continues to expose `getOrCreate`, `append`, `checkpoint`, and
`close`. It creates a `SegmentedPartitionLog` instead of a
`FilePartitionLog`. `PartitionLog` remains the broker-facing abstraction, so
no broker protocol, request handler, producer, or consumer API changes are
required.

`LogManager` 继续对外提供 `getOrCreate`、`append`、`checkpoint` 和 `close`。它创建 `SegmentedPartitionLog`，不再创建 `FilePartitionLog`。`PartitionLog` 仍是面向 broker 的抽象，因此无需更改 broker 协议、请求处理器、生产者或消费者 API。

```text
append(topic, partition, key, value)
  -> allocate next absolute offset
  -> WriteAheadLog.append(DATA_APPEND)
  -> SegmentedPartitionLog.appendAt(offset)
  -> append record to active segment
  -> update sparse index when its stride is reached
  -> apply V2.0 flush and checkpoint policies

startup
  -> open and validate partition catalogs and segments
  -> recover an incomplete tail only in the active highest-base segment
  -> rebuild a missing or invalid sparse index from its valid log segment
  -> replay WAL from the valid V2.0 checkpoint position
  -> write the next checkpoint using segmented high watermarks
```

### On-Disk Layout / 磁盘布局

Each partition moves from the legacy file
`{dataDir}/{topic}-{partition}.log` to a dedicated directory:

每个分区从旧版文件 `{dataDir}/{topic}-{partition}.log` 迁移到独立目录：

```text
{dataDir}/segments/{topic}-{partition}/
  catalog.json
  00000000000000000000.log
  00000000000000000000.index
  00000000000000001024.log
  00000000000000001024.index
```

A segment filename is the zero-padded absolute base offset. The highest-base
segment is active and appendable. Lower-base segments are sealed and
immutable. `catalog.json` records the catalog generation, active base offset,
ordered segment bases, and each segment creation time. It is written to a temp
file, forced, and atomically replaced.

segment 文件名是以零填充的绝对 base offset。base offset 最大的 segment 为活动 segment，可以追加写入；base offset 较小的 segment 均已封闭且不可变。`catalog.json` 记录目录代次、活动 base offset、按顺序排列的 segment base，以及每个 segment 的创建时间。写入时先生成临时文件，强制落盘后再原子替换。

The record encoding remains compatible with `FilePartitionLog`:

记录编码继续与 `FilePartitionLog` 兼容：

```text
[offset: long][keyLength: int][key bytes][valueLength: int][value bytes]
```

Offsets must be strictly increasing within every physical segment and across
the catalog order. They are no longer required to be contiguous. This lets
V2.1.1 remove obsolete records while preserving their original offsets.

每个物理 segment 内以及目录顺序中的 offset 都必须严格递增，但不再要求连续。这样 V2.1.1 可以删除过期记录，同时保留记录的原始 offset。

An index entry is fixed width:

索引项采用固定宽度：

```text
[offset: long][filePosition: long]
```

The index records one entry per configured record stride. A fetch selects the
greatest catalog base at or below `fromOffset`, seeks to the largest indexed
offset not greater than `fromOffset`, and scans forward across later segments
until `maxBytes` is reached.

索引按配置的记录步长写入一项。fetch 会选择不大于 `fromOffset` 的最大目录 base，定位到不大于 `fromOffset` 的最大索引 offset，然后向后扫描后续 segment，直至达到 `maxBytes`。

### Rolling And Configuration / 滚动与配置

V2.1.0 adds a `SegmentedLogConfig` owned by `LogManagerConfig`. Its initial
settings are:

V2.1.0 新增由 `LogManagerConfig` 持有的 `SegmentedLogConfig`。初始设置如下：

| Setting / 设置 | Default / 默认值 | Rule / 规则 |
| --- | --- | --- |
| `segmentMaxBytes` | 64 MiB | Roll before an append that would exceed the limit when the active segment already has a record. A single oversized record is allowed in its own segment. / 当活动 segment 已有记录时，如果下一次追加会超过限制，则在追加前滚动。单条超大记录允许独占一个 segment。 |
| `sparseIndexIntervalRecords` | 64 | Write an index entry for the first record and then every configured stride. / 为第一条记录写入索引项，此后按配置步长写入。 |

The existing two-argument `LogManagerConfig(FlushPolicy, int)` constructor
remains as a compatibility overload and supplies the default
`SegmentedLogConfig`.

现有的双参数构造函数 `LogManagerConfig(FlushPolicy, int)` 继续作为兼容重载，并提供默认 `SegmentedLogConfig`。

### Recovery And Corruption Boundaries / 恢复与损坏边界

- A missing catalog is rebuilt from correctly named segment pairs in ascending
  base-offset order.
  缺失的目录根据命名正确的 segment 文件对，按 base offset 升序重建。
- A missing or corrupt index is rebuilt by scanning its corresponding valid log
  segment. The log is never reconstructed from an index.
  缺失或损坏的索引通过扫描对应的有效日志 segment 重建；绝不根据索引重建日志。
- An incomplete tail is truncated only in the active highest-base segment.
  不完整的尾部只会在 base 最大的活动 segment 中被截断。
- Structural corruption, a non-increasing offset, an invalid field length,
  catalog/filename disagreement, or a corrupt sealed segment fails startup
  with a storage-specific error.
  结构损坏、offset 非递增、字段长度无效、目录与文件名不一致，或已封闭 segment 损坏，都会使启动失败并返回存储专用错误。
- A valid V2.0 checkpoint is accepted only when segmented partition high
  watermarks meet or exceed its values. Otherwise WAL replay starts at zero,
  following the existing V2.0 safety rule.
  只有当分段分区的高水位不低于有效 V2.0 检查点中的值时，才接受该检查点；否则按照现有 V2.0 安全规则，从零开始重放 WAL。

### Legacy Migration / 旧版迁移

On the first open of a partition that has a legacy
`{topic}-{partition}.log` and no segmented catalog, `LogManager` migrates it
to a staging partition directory. Records are copied in offset order using the
new segment writer, segments and indexes are forced, then the catalog is
atomically published. The original legacy file remains until the segmented
catalog has been reopened successfully and a checkpoint has been saved; it is
then deleted.

首次打开具有旧版 `{topic}-{partition}.log` 但没有分段目录的分区时，`LogManager` 会将其迁移到暂存分区目录。记录按照 offset 顺序使用新的 segment writer 复制；segment 和索引强制落盘后，再原子发布目录。原始旧版文件会一直保留，直到分段目录成功重新打开且检查点已保存，随后才删除。

If a process stops before catalog publication, startup removes the staging
directory and retries from the unchanged legacy file. If publication succeeded
but cleanup did not, the valid catalog wins and startup safely removes the
leftover legacy file after validation. This makes migration restartable without
dropping V2.0 data.

如果进程在目录发布前停止，启动时会删除暂存目录，并从未改动的旧版文件重试。如果目录已发布但清理未完成，则以有效目录为准；验证后，启动流程会安全删除遗留的旧版文件。这样可以在不丢失 V2.0 数据的前提下重新开始迁移。

## V2.1.1 Maintenance Architecture / V2.1.1 维护架构

V2.1.1 adds a single maintenance coordinator per `LogManager`. It has one
serialized execution path for retention and compaction, starts only when a
maintenance policy is enabled, and is stopped before logs close. The public
data path remains synchronous.

V2.1.1 为每个 `LogManager` 增加一个维护协调器。保留和压缩共用一条串行执行路径；只有启用维护策略时才启动，并在日志关闭前停止。公共数据路径继续采用同步方式。

### Retention / 保留策略

`RetentionPolicy` supports independent `retentionMs` and `retentionBytes`
limits. It selects only the oldest sealed segments. It never deletes the active
segment, the final readable segment, or a segment pinned by an in-flight read
snapshot. After files are removed, it atomically publishes a replacement
catalog with the new `logStartOffset`.

`RetentionPolicy` 支持相互独立的 `retentionMs` 和 `retentionBytes` 限制。它只选择最旧的已封闭 segment，绝不删除活动 segment、最后一个可读 segment，或被进行中读快照固定的 segment。文件删除后，它会原子发布包含新 `logStartOffset` 的替代目录。

### Compaction / 压缩

`SegmentCompactor` operates on a selected contiguous window of sealed
segments. It reads records from newest to oldest, including later catalog
segments when determining whether a key is obsolete. For each non-null key it
keeps only the newest record. Records with a null key are always retained.

`SegmentCompactor` 在选定的连续已封闭 segment 窗口上运行。它从新到旧读取记录，并在判断某个 key 是否过期时纳入目录中更晚的 segment。对于每个非 null key，只保留最新记录；key 为 null 的记录始终保留。

Compaction writes replacement `.cleaned` log and index pairs, forces them,
validates their records, and publishes one replacement catalog generation.
Only after that catalog swap may obsolete files be deleted. Compacted records
retain their original absolute offsets, so holes are expected and fetch must
scan past them.

压缩会写入替代的 `.cleaned` 日志和索引文件对，强制落盘并验证其中记录，然后发布一个替代目录代次。只有目录完成切换后，才可以删除旧文件。压缩后的记录保留原始绝对 offset，因此允许出现 offset 空洞，fetch 必须能够越过这些空洞继续扫描。

### Reader And Writer Safety / 读写安全

Readers use an immutable `SegmentCatalog` snapshot for one `read` call. The
append path writes only the active segment. Maintenance holds the partition
maintenance lock while publishing a new catalog and delays deletion until no
reader holds the prior snapshot. This keeps a reader from observing a partially
rewritten segment set.

每次 `read` 调用期间，reader 使用不可变的 `SegmentCatalog` 快照。追加路径只写活动 segment。维护流程在发布新目录时持有分区维护锁，并延迟删除，直到没有 reader 持有旧快照。这可以避免 reader 观察到只完成部分重写的 segment 集合。

## Error Handling / 错误处理

- Invalid sizes, index strides, retention limits, and compaction configuration
  fail at `LogManagerConfig` construction with actionable messages.
  无效的大小、索引步长、保留限制和压缩配置会在构造 `LogManagerConfig` 时失败，并给出可操作的错误信息。
- Storage format errors include the partition, segment base offset, and byte
  position where applicable.
  在适用情况下，存储格式错误会包含分区、segment base offset 和字节位置。
- Failed catalog replacement leaves the prior catalog and segment set readable;
  temporary staging or `.cleaned` files are ignored and cleaned during the
  next startup validation.
  目录替换失败时，旧目录和 segment 集合仍可读取；临时暂存文件或 `.cleaned` 文件会被忽略，并在下次启动验证时清理。
- WAL replay uses `appendAt` idempotence. An equal record already present at an
  offset succeeds; a different record at that offset is a recovery failure.
  WAL 重放利用 `appendAt` 的幂等性。如果某 offset 已存在相同记录，则视为成功；如果该 offset 存在不同记录，则恢复失败。

## Test Strategy / 测试策略

### V2.1.0

- `SegmentedPartitionLogTest`: roll boundary, oversized record, reads across
  segments, reopen recovery, active-tail truncation, sealed corruption failure,
  and non-contiguous offsets.
  `SegmentedPartitionLogTest`：覆盖滚动边界、超大记录、跨 segment 读取、重新打开恢复、活动尾部截断、已封闭 segment 损坏失败，以及不连续 offset。
- `SparseOffsetIndexTest`: first-entry creation, stride behavior, seek nearest
  entry, missing-index rebuild, corrupt-index rebuild, and index/log mismatch.
  `SparseOffsetIndexTest`：覆盖首个索引项创建、步长行为、定位最近索引项、缺失索引重建、损坏索引重建，以及索引与日志不匹配。
- `LogManagerSegmentRecoveryTest`: WAL replay after rolling, checkpoint
  validation, idempotent replay, and legacy single-file migration including
  interrupted staging recovery.
  `LogManagerSegmentRecoveryTest`：覆盖滚动后的 WAL 重放、检查点验证、幂等重放，以及包括暂存中断恢复在内的旧版单文件迁移。
- `BrokerConfigTest`: default values, CLI/config parsing, and invalid segment
  settings.
  `BrokerConfigTest`：覆盖默认值、CLI/配置解析和无效 segment 设置。

### V2.1.1

- `RetentionPolicyTest`: time and size selection, active-segment protection,
  minimum-readable-segment protection, and atomic catalog publication.
  `RetentionPolicyTest`：覆盖按时间和大小选择、活动 segment 保护、最少可读 segment 保护，以及目录原子发布。
- `SegmentCompactorTest`: latest non-null key survives, null keys survive,
  original offsets are preserved, and compacted output is recoverable.
  `SegmentCompactorTest`：验证最新非 null key 记录保留、null key 记录保留、原始 offset 保持不变，以及压缩输出可恢复。
- `LogManagerMaintenanceTest`: retention/compaction lifecycle, concurrent read
  snapshot safety, restart cleanup of temporary files, and WAL recovery after
  a catalog replacement.
  `LogManagerMaintenanceTest`：覆盖保留/压缩生命周期、并发读快照安全、重启时清理临时文件，以及目录替换后的 WAL 恢复。

All new behavior follows test-driven development: each test is run red before
the corresponding production code is added. The module and full-reactor Maven
verification must retain the existing 90 percent JaCoCo line-coverage gate.

所有新增行为均遵循测试驱动开发：先运行对应测试并确认失败，再添加生产代码。模块级和完整 Maven reactor 验证必须继续满足现有 90% JaCoCo 行覆盖率门槛。
