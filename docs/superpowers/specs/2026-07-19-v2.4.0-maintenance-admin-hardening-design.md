# MiniMQ V2.4.0 Maintenance Admin Hardening Design

**Status:** Approved for implementation

## Summary

V2.4.0 already exposes maintenance report, execution, and metrics through broker
protocol APIs 13-15 and the demo CLI. This hardening pass keeps the project at
V2.4.0 and addresses the review findings before merge:

1. remove maintenance planning and execution from the Netty worker thread;
2. require explicit authorization for every maintenance admin API;
3. make the CLI accept one explicit broker instead of silently selecting the
   first address from a plural option;
4. test enabled retention and compaction through real protocol and CLI paths;
5. add readable client API names for keys 13-15.

The implementation branch will use the requested `dev/` prefix. No new project
version, release tag, or test-report version will be created; the existing
V2.4.0 test report will be updated in place.

## Chosen Approach

Add one broker-scoped `MaintenanceAdminService`. It owns authorization, a
dedicated single-thread executor, destructive-run admission, and shutdown. This
keeps resource ownership in `BrokerServer` and leaves `MqRequestHandler`
responsible only for protocol routing and response mapping.

This approach was selected over:

1. a Netty `EventExecutorGroup`, which would couple maintenance admission and
   lifecycle to pipeline scheduling; and
2. an executor owned by each handler, which would fragment concurrency control
   across channels and make shutdown unreliable.

## Configuration And Authorization

`BrokerConfig` gains a required `adminToken` parsed from `--admin-token`.
Missing, empty, or whitespace-only values fail broker configuration before any
network listener starts.

`MaintenanceReportRequest`, `MaintenanceRunRequest`, and
`MaintenanceMetricsRequest` each carry the token. `ProtocolSerdes` writes and
reads it as a normal length-prefixed UTF-8 string. The service compares the
configured and supplied UTF-8 bytes with `MessageDigest.isEqual`; it does not
use ordinary `String.equals` for authorization.

All three APIs require authorization. A missing or incorrect token returns the
new protocol error `UNAUTHORIZED`. No report, metric snapshot, or maintenance
work is performed after failed authorization. Tokens and complete
`BrokerConfig` or request objects must not be logged.

## Service And Threading Model

`BrokerServer` creates one `MaintenanceAdminService` after `PartitionManager`
and injects that same instance into every `MqRequestHandler`. The service uses
one named daemon thread and a queue capacity of one so maintenance work cannot
consume Netty EventLoop threads or build an unbounded backlog. At most one task
executes and one task waits.

The operation behavior is:

| Operation | Execution | Admission |
| --- | --- | --- |
| report | dedicated executor | reject with `MAINTENANCE_BUSY` when the bounded executor cannot accept it |
| run | dedicated executor | at most one run may be running or queued; another run returns `MAINTENANCE_BUSY` immediately |
| metrics | caller thread after authorization | immutable in-memory snapshot; no executor hop |

The run admission flag is acquired before submission and released in every
completion, rejection, and exception path. Executor rejection while the broker
is stopping also maps to `MAINTENANCE_BUSY`.

The service returns asynchronous results to the handler. The handler schedules
response encoding and `writeAndFlush` through `ctx.executor()`, preserving the
original channel and correlation ID. Maintenance failures are logged by the
broker and retain the current `INVALID_REQUEST` protocol response; this pass
does not introduce a general internal-error taxonomy.

## Lifecycle

`BrokerServer.stop()` performs shutdown in this order:

1. close the server channel so no new admin requests are accepted;
2. shut down the maintenance service, wait five seconds for accepted work, then
   interrupt it if necessary and wait for the maintenance thread to terminate;
3. stop Netty worker groups and replication services;
4. close `PartitionManager` and its storage resources.

`PartitionManager` is not closed while the maintenance thread is still alive,
even if interruption takes longer than the initial five-second grace period.
This ordering prevents maintenance tasks from accessing closed logs. Service
shutdown is idempotent so partial broker startup and repeated cleanup remain
safe.

## CLI Contract

Only `maintenance-report`, `maintenance-run`, and `maintenance-metrics` change
from `--brokers` to the singular, required `--broker host:port`. The existing
create, produce, and consume commands keep `--brokers` because their clients
support multiple bootstrap addresses.

Each maintenance command also requires `--admin-token`. The CLI rejects a
comma-separated broker value, a missing host or port, and a port outside
1-65535 before opening a connection. Before sending the request it prints:

```text
Maintenance target: host:port
```

It never prints the token. Protocol failures continue through
`NetworkClient.ensureSuccess`, now producing readable `UNAUTHORIZED` and
`MAINTENANCE_BUSY` errors. `NetworkClient.apiName()` maps API keys 13, 14, and
15 to maintenance report, run, and metrics names.

## Protocol Compatibility

API keys 13-15 were introduced on the unmerged V2.4.0 branch, so adding the
token fields corrects their V2.4.0 wire contract rather than creating a new API
version. The common error enum adds stable numeric values for `UNAUTHORIZED`
and `MAINTENANCE_BUSY`; existing values 0-6 do not change.

Older builds of the unmerged V2.4.0 branch cannot call the hardened APIs because
their empty request bodies fail decoding or authorization. This incompatibility
is intentional: unauthenticated maintenance requests must not remain valid.

## Test Strategy

Development follows a red-green-refactor sequence for each behavior group.

- `BrokerConfigTest` covers missing, blank, and valid `--admin-token` values.
- `ProtocolSerdesTest` covers request-token round trips and both new error codes.
- `MaintenanceAdminServiceTest` proves authorization, execution on the named
  maintenance thread, immediate busy responses for overlapping runs, rejection
  during shutdown, and admission-flag release after failure.
- `EmbeddedBrokerChannelTest` covers authorized and unauthorized handler paths,
  asynchronous correlation-ID preservation, busy mapping, and a non-empty
  `MaintenanceSegmentInfo` response.
- `DemoCliTest` covers required singular arguments, comma rejection, target
  output, and unauthorized output. Real TCP tests create small sealed segments
  under separate deterministic configurations: size retention must expose a
  `DELETE` segment, and keyed compaction must expose a `COMPACT` segment through
  report or run output. The tests no longer establish coverage only through
  `SKIPPED_DISABLED`.
- Client tests cover readable names for APIs 13-15.

Focused module tests run after each implementation group. Final acceptance runs:

```text
mvn clean verify -gs .mvn/settings.xml -s .mvn/settings.xml
```

The existing JaCoCo gates must pass, and the V2.4.0 test report plus relevant
testing and usage documentation must reflect the final commands and results.

## Open Risks

- The MiniMQ protocol does not provide TLS. A shared token prevents callers who
  do not know the secret from invoking maintenance, but it does not prevent a
  network observer from capturing the token. TLS is outside this hardening pass.
- Supplying `--admin-token` on a command line can expose it to same-host process
  inspection. Environment-variable or secret-file loading is deferred to avoid
  expanding the V2.4.0 scope.
- Report and run share one bounded executor. A long operation can temporarily
  produce `MAINTENANCE_BUSY` for another admin request; callers must retry.
