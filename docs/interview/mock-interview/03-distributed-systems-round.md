# 分布式系统模拟轮

完整参考见 [一致性与事务](../distributed-systems/01-consistency-idempotency-and-transaction.md) 和 [治理与可观测性](../distributed-systems/02-high-availability-and-governance.md)。

## Q1：接口超时后如何避免重复下单？

**主答**：超时是未知结果，不能直接重放。请求带业务幂等键，订单库以唯一约束和处理记录作为最终事实；先查已有结果。跨服务通过本地事务 + Outbox 发布事件，消费者 Inbox 去重并用状态机推进。用户得到“处理中”和查询入口。

**追问**：若客户端用同一 key 传不同参数？答：记录请求摘要，检测冲突并拒绝；不能把不同意图合并。

## Q2：数据库提交成功但发送 MQ 失败怎么办？

**主答**：不要把 DB 写和 MQ 发送当作两个无保护的顺序操作。业务数据和 Outbox 事件在同一 DB 事务写入，事务提交后由发布器/CDC 可靠投递；允许重复，所以消费者幂等。监控未发布量、最老事件年龄、失败次数与死信。

**追问**：为什么不直接 2PC？答：跨资源协调会引入阻塞、耦合和可用性成本；多数业务可接受最终一致，选择可补偿、可观测的本地事务方案。强协调需求需按资源和业务重新评估。

## Q3：如何设计一次大促保护系统？

**主答**：先压测核心链路的峰值、缓存冷启动、节点丢失和依赖变慢。入口按用户/接口分级限流，核心链路与非核心隔离；缓存预热，慢依赖设置 deadline、有限重试+抖动、舱壁和熔断。过载时返回降级或排队，关键写无法保证正确性时明确失败，不伪造成功。

**追问**：为什么不能多层重试？答：每层重试会相乘放大下游流量，故集中在一个明确层级并设 retry budget。

## Q4：如何排查分布式链路偶发慢？

**主答**：从入口 requestId/traceId 关联 Trace、Metrics、Logs。先确认慢请求占比、哪个 span 占时、是否有重试/排队，再看对应服务的线程池、GC、连接池和下游指标。日志记录离散异常，指标看趋势/告警，链路追踪定位一次请求；避免在 metric 标签放订单号等高基数值。

## Q5：Saga 如何处理补偿失败？

**主答**：补偿也是业务操作，必须幂等且有状态记录。失败后有限重试、退避、告警，进入可人工介入的中间态；不能假设补偿必定成功。对不可逆动作设计反向业务动作或人工审核，并让用户状态可解释。

## Q6：CAP 怎么结合业务回答？

**主答**：CAP 只讨论分区存在时的一致性和可用性取舍。支付/库存关键不变量优先正确性，必要时返回处理中或失败；推荐/浏览允许最终一致和稍旧数据。进一步说明副本读、超时、补偿、用户提示与监控，而非只背“CP/AP”。

## 5 分钟系统设计题：订单创建链路

```text
入口鉴权/限流 → 订单服务（幂等键、订单事务、Outbox）
                    ↓
                 MQ 事件
             ↙                  ↘
库存服务（预留/幂等）       支付服务（渠道幂等）
             ↘                  ↙
          状态机、补偿、通知/查询
```

回答顺序：

1. 澄清：峰值、库存语义、支付是否同步、是否允许处理中、RPO/RTO。
2. 正确性：订单幂等号、库存条件更新/预留、支付流水唯一、状态机。
3. 可靠事件：Outbox、至少一次、消费者去重、失败重试/死信/对账。
4. 可用性：限流、缓存、超时、bulkhead、熔断、降级和容量。
5. 观测：成功率、延迟、积压、未发布事件、中间态、按 trace/订单关联排查。
6. 边界：不用声称全链路瞬时强一致；说明最终一致窗口和补偿策略。
