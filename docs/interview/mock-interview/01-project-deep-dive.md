# 项目深挖：MiniMQ

## 开场题：请介绍一个你最有代表性的项目

**90 秒回答骨架**

“我选择 MiniMQ。它是一个用 Java 实现的消息队列项目，目标是把 Broker 的核心链路拆清楚：协议编解码、生产消费、主题/队列语义、持久化、确认重投以及恢复。我的重点不只是实现 API，而是围绕消息不丢、重复可处理和故障后恢复这些语义组织模块与测试。项目让我把 Java NIO/Netty、并发控制、日志持久化和端到端测试连在一起。若迁移到业务系统，我会进一步配合数据库幂等、Outbox、监控和运维治理，保证业务侧的最终一致。”

**不要说**：未经验证的吞吐量、生产规模、跨服务事务已落地，或“保证绝对 exactly-once”。

## 追问链 1：消息为什么不会丢？

1. **Q：从生产到消费有哪些阶段？**
   - A：区分生产端发送、Broker 接收与持久化、消费端处理和确认；每一步失败语义不同，不能只看一处 ack。
2. **Q：持久化成功就等于业务成功吗？**
   - A：不等于。Broker 的持久化解决消息存活；消费者业务提交和确认之间仍会产生重复投递，因此业务必须幂等。
3. **Q：宕机恢复如何验证？**
   - A：通过恢复测试验证可恢复日志/元数据、未完成消息的重投和消费确认状态；报告具体测试与实际结果，不虚报线上演练。
4. **Q：如何用于订单业务？**
   - A：订单库本地事务写业务数据与 Outbox，事件经 MQ 投递；库存/支付消费者以唯一 ID 和状态机幂等处理。

## 追问链 2：为什么要有确认与重投？

1. **Q：消费者处理成功但确认前宕机怎么办？**
   - A：Broker 可能重投，故传输层通常至少一次；消费者用幂等记录/唯一约束让重复不重复生效。
2. **Q：那能否做到 exactly-once？**
   - A：先限定边界。Broker 的去重/事务能力不自动覆盖数据库和外部调用；业务端通常通过至少一次 + 幂等达成“效果上一次”。
3. **Q：反复失败的消息怎么办？**
   - A：有限重试、退避、死信/隔离、告警与人工处置；不能无限重试拖垮消费者。

## 追问链 3：如何定位性能问题？

1. 先判断是端到端延迟、Broker 吞吐、磁盘、网络、消费者处理还是积压。
2. 分层看生产速率、消费速率、积压、P95/P99、GC、线程池/事件循环、磁盘 fsync 和网络连接指标。
3. 用基准与压测固定输入，再逐项改变批量、并发、刷盘策略或消费者数；记录对延迟和可靠性语义的影响。
4. 不直接把“异步”说成更快：异步也会引入排队、内存和故障恢复的取舍。
