# 完整参考问答

适用：3 年以上 Java 后端社招。答案可直接阅读、理解后再改成自己的语言；涉及 MiniMQ 时只陈述项目证据，业务方案不虚构成线上经历。

## 1. 请介绍一下 MiniMQ 项目

MiniMQ 是一个用 Java 实现的消息队列项目。我关注的是 Broker 的核心链路：协议编解码、生产与消费、主题/队列语义、持久化、确认重投和宕机恢复。项目价值不只是实现 API，而是把“消息何时算可靠、失败后会发生什么、消费者为什么必须幂等”这些语义拆清楚，并通过测试验证。

我会将其划分为网络与协议、消息存储、投递调度和管理边界。网络层负责连接与帧处理，存储层负责持久化和恢复，投递层处理确认、重投和消费状态。这样问题可以分层定位。迁移到真实订单系统时，我会在业务库补充 Outbox、唯一约束、消费者幂等和观测体系。

## 2. 消息为什么不能只靠 Broker 确认保证不重复？

确认只覆盖一个阶段，完整链路包括生产发送、Broker 持久化、消费者处理和消费者确认。消费者可能已提交业务事务，却在确认前宕机；Broker 不知道业务是否完成，会重投消息。因此传输层通常按至少一次设计，最终由消费者通过业务幂等键、唯一索引、处理记录或状态机保证重复消息不重复生效。

## 3. `volatile` 能代替锁吗？

不能。`volatile` 提供可见性和一定的有序性，适合停止标志、配置刷新等单状态发布；它不保证复合操作原子性，`count++` 仍会丢更新。若是原子计数可用原子类；若有“检查后更新”或跨字段不变量，则用锁、CAS 循环或串行化。高竞争下 CAS 自旋也会浪费 CPU，不能把无锁等同于更快。

## 4. 如何配置线程池？

先按 CPU 密集、IO 等待、下游容量和可接受队列时间拆分任务池。CPU 密集任务线程数通常接近可用核心数；IO 任务可适当增加，但仍受数据库、HTTP 下游、内存和文件描述符约束。不同依赖用隔离线程池/连接池，防止一个慢接口耗尽全局资源。

队列、最大线程和拒绝策略必须有界，并监控活跃线程、排队时间、拒绝数和任务耗时。无限队列只是把慢依赖变成内存压力与超时雪崩；过载时应明确拒绝、排队或降级语义。

## 5. 线上 Full GC 频繁怎么排查？

先确认影响：P99、错误率、CPU、堆曲线与 GC 停顿，判断是内存泄漏、突发大对象、分配过快还是配置问题。再用 GC 日志看年轻代/老年代回收和晋升，用 heap dump、分配分析定位对象来源。常见根因包括无界缓存/队列、连接或 ThreadLocal 未释放、大响应聚合。

修复回到对象生命周期和流量控制：队列设上限、流式/分页处理、限制缓存、修复引用链。JVM 参数要以证据和压测验证，不能先盲目增大堆。

## 6. Kafka 和 RocketMQ 如何选型？

先看业务语义、吞吐特征、生态和团队运维能力。日志采集、流式计算和大规模事件流通常会关注 Kafka 的分区与生态；业务消息若依赖延迟、事务消息等能力，可评估 RocketMQ。无论选哪个，都必须设计顺序范围、重复投递、积压、失败重试、死信和监控，不能只按产品名决策。

## 7. 如何保证消息顺序？

先定义顺序粒度。全局顺序需要单一串行通道，吞吐和可用性代价高；常见要求是同订单、同用户或同业务键有序。将业务键作为路由键，让同一键进入同一分区/队列，并在该分区内按序消费，通常更合理。

还要说明边界：扩分区、重试、消费并发、失败跳过和跨分区聚合都会影响顺序；消费者状态机应拒绝非法状态迁移或处理缺失事件，不能只依赖“理论上有序”。

## 8. Redis 与数据库如何保持一致？

常用 Cache Aside。读请求先查 Redis，未命中时回源数据库并带 TTL 写缓存；写请求先在数据库事务中提交，把数据库作为事实来源，再删除缓存。删除而非直接更新缓存可以减少并发覆盖和部分字段更新复杂度。

它并非绝对强一致：删除失败或并发旧读回填都会形成短暂窗口。数据库提交后应有限重试删除，并通过可靠消息或补偿任务收敛；强一致的少数读绕过缓存或携带版本。必须明确可接受窗口，不能声称天然一致。

## 9. 缓存穿透、击穿、雪崩如何处理？

穿透是查询不存在的数据不断回源，用参数校验、短 TTL 空值、布隆过滤器和限流；布隆过滤器有假阳性，不能当最终事实。击穿是热点 key 失效瞬间并发回源，用 single-flight、逻辑过期异步刷新和预热。雪崩是大量 key 同时过期或 Redis 故障，用 TTL 抖动、限流、熔断、降级、多级缓存和数据库隔离。共同原则是先保护数据库。

## 10. Redis 分布式锁有哪些关键点？

加锁使用 `SET key token NX PX ttl`，一次命令同时保证仅在 key 不存在时设置并带过期时间；token 必须是每次获取锁生成的唯一值。释放时不能直接 `DEL`，而要原子比较 token 后删除，否则旧持有者在租约到期后恢复执行，可能删除新持有者的锁。

锁只能降低竞争，不能替代业务正确性。主从异步复制故障切换时可能双持锁；扣库存、扣款仍要以数据库条件更新、唯一约束、幂等键或围栏令牌兜底。长任务优先拆分或异步化，续期不等于永远安全持锁。

## 11. 如何设计联合索引？

从真实高频 SQL 的等值条件、范围条件、关联、排序和返回列出发。一般等值过滤列在前，范围列通常靠后，再考虑排序与覆盖索引。例如按租户、状态和时间查订单，`(tenant_id, status, created_at)` 可以是候选，但必须用真实参数的执行计划和耗时验证。

最左前缀不是机械规则。索引 `(a,b,c)` 能用于以 `a` 开始的检索，范围条件之后的列常难继续缩小扫描；同时索引会增加写成本、空间和维护成本。最终要比较扫描行、回表、排序、返回行和写入影响。

## 12. 慢 SQL 怎么排查和优化？

先从慢日志和接口指标确认影响范围与参数分布，用真实脱敏参数执行 `EXPLAIN` / `EXPLAIN ANALYZE`，观察扫描、索引、排序临时表、返回行与锁等待。也看数据库 CPU、IO、连接池和并发，排除只是某次流量尖峰。

优先做最小且可验证的改变：补/调整索引、改写使条件可走索引、减少列、限制结果集、seek 分页解决深翻页、更新统计信息。之后压测、灰度并观察读延迟和写成本；强制索引只是有证据的临时兜底。

## 13. RR 下 `FOR UPDATE` 为什么可能锁住很多行？

InnoDB 的锁基于实际扫描到的索引记录与范围，不是只锁最终返回行。默认可重复读下，范围扫描可能使用 next-key lock，即记录锁加前方间隙锁，用于防止范围内插入造成的幻读。缺合适索引、范围条件或非唯一条件都可能扩大扫描和锁范围。

排查先看隔离级别和执行计划，再通过合适索引、唯一等值条件、缩短事务和统一更新顺序降低影响。

## 14. 如何避免超卖？

数据库是最终防线，可执行 `UPDATE stock SET available = available - ? WHERE sku_id = ? AND available >= ?`，通过受影响行数判断是否成功；这把库存不能为负放进单条原子条件更新。订单请求还应带幂等号，并在订单表建立唯一约束，防止超时重试重复下单。

Redis 可做预热、限流或前置预扣来缓解热点，但不能是唯一事实来源。异步订单链路还需消费者幂等、失败补偿和对账。

## 15. 数据库写成功但发送 MQ 失败怎么办？

不能把更新数据库和发 MQ 当成两个无保护的顺序动作：先发可能消费到最终回滚的数据，后发会在进程崩溃时丢事件。使用 Transactional Outbox：业务数据变更与待发送事件记录在同一个本地数据库事务中；提交后由后台发布器或 CDC 投递。发布器可能重复发送，所以消费者仍要按事件 ID、唯一约束或状态机幂等。

Outbox 还要有索引、分批拉取、失败重试、积压告警、清理归档和同聚合顺序策略。可靠性来自“本地原子写 + 可重试发布 + 幂等消费 + 可观测”。

## 16. Saga、TCC 和 2PC 怎么选？

多数跨服务业务优先本地事务加 Outbox，再用 Saga 做最终一致：各服务独立提交本地事务，失败时执行业务补偿。它适合长流程和服务自治，但必须设计中间态、超时、补偿、幂等和人工介入。TCC 适用于资源能明确预留且参与者可实现 Try/Confirm/Cancel 的场景，代价是接口侵入和空回滚、悬挂、冻结等复杂度。

2PC/XA 仅在参与资源有限、确有强协调需求且可接受阻塞和运维成本时评估，不是默认方案。先看业务是否允许最终一致与补偿，再选方案。

## 17. 下游服务变慢，如何避免服务雪崩？

设置端到端 deadline 并向下游传递剩余预算；连接、读写和排队都要有上限。仅对幂等且临时性的失败做有限次指数退避加随机抖动重试，避免网关、服务、客户端多层同时重试。

不同下游和核心/非核心业务使用独立线程池、连接池或并发阈值隔离；失败率或慢调用达到阈值后熔断，快速返回缓存、默认值、排队结果或“处理中”。过载时优先限流/负载丢弃，恢复时半开探测并观察重试、队列和延迟是否回落。

## 18. 如何建设可观测性？

指标看趋势与告警，日志记录离散异常，Trace 定位一次跨服务请求。最小集合包括请求量、错误率、延迟分位数、线程/连接/队列饱和度；也要有下游成功率、超时重试、熔断状态、慢查询、MQ 积压、订单成功率和 Outbox 未发布量。

入口生成或透传 requestId/trace context，HTTP 和 MQ header 继续传递；日志带 traceId、业务 ID、错误码，方便拉通时间线。指标标签避免订单号、用户 ID、完整 URL 等高基数值，否则监控系统会先出现容量问题。

## 19. 如何回答 CAP？

CAP 讨论的是网络分区出现时一致性与可用性的取舍，不是日常架构只选两个字母。支付、扣库存等关键不变量优先正确性，无法确认时返回失败或处理中；推荐、浏览等读服务可接受短暂旧数据来保持可用。继续落到副本读策略、超时、补偿、用户提示与监控，才是完整答案。

## 20. 如何设计订单创建链路？

入口先做鉴权、参数校验、幂等键和分级限流。订单服务在本地事务中创建订单和 Outbox 事件；发布器投递订单创建事件。库存服务按订单号幂等预留，支付服务以支付流水和渠道幂等 token 发起/查询支付，所有服务通过状态机进行条件迁移。失败事件进入重试、死信、补偿和对账流程，用户在未知状态下看到“处理中”并可查询。

高可用方面，支付和库存等下游隔离，设置 deadline、有限重试、熔断和降级；大促前做容量与故障演练。观测方面，按订单号、requestId、traceId 和事件 ID 串联订单库、Outbox、MQ 与消费者，监控成功率、延迟、积压和中间态。关键是追求业务不变量和可收敛的最终一致，而不是声称所有服务瞬时强一致。
