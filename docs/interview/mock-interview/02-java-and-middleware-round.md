# Java 与中间件模拟轮

每题先用 30–60 秒回答主线，再接受追问。完整参考见 [Java Q&A](../java-backend/04-java-backend-qa.md)、[MQ](../middleware/message-queue/03-scenarios-and-qa.md)、[Redis](../middleware/redis/03-scenarios-and-qa.md)、[MySQL](../middleware/mysql/03-scenarios-and-qa.md)。

## Java 基础与并发

### Q1：`volatile` 能替代锁吗？

**答题骨架**：`volatile` 提供可见性与一定的有序性，不提供复合操作的原子性。状态标记、配置刷新可用；`count++`、检查后执行等需要 CAS、锁或原子类。选择时先看共享状态不变量和竞争强度。

**追问**：CAS 的 ABA 和自旋开销？答：ABA 可用版本戳等识别；高竞争下自旋会浪费 CPU，应考虑分段、队列化或锁。

### Q2：线程池如何配置？

**答题骨架**：先按 CPU 密集/IO 等待、下游容量与可接受队列时间拆分任务池；队列和最大线程都必须有界，明确拒绝策略、监控活跃线程/排队/拒绝数。不能以无限队列掩盖下游慢。

### Q3：线上 Full GC 频繁怎么排查？

**答题骨架**：看 GC 日志、堆使用曲线、对象分配率、晋升和停顿时间；结合 heap dump/火焰图定位泄漏或突发大对象。先保护流量和内存，再修对象生命周期、缓存/队列无界或参数配置；不先盲调 JVM 参数。

## 消息队列

### Q4：Kafka 和 RocketMQ 怎么选？

**答题骨架**：先看场景而非品牌。高吞吐日志流/流式生态倾向 Kafka；业务消息、延迟/事务消息等需结合 RocketMQ 能力与运维条件。无论选择哪个，都要设计重复、积压、顺序和死信处理。

### Q5：如何保证顺序？

**答题骨架**：先定义是全局、分区还是同业务键顺序。通常按订单 ID 等业务键路由到同一分区/队列，单分区内顺序消费；扩容、重试、跨分区和并发消费者会影响保证范围。全局顺序吞吐代价高。

### Q6：消息积压怎么处理？

**答题骨架**：先算生产-消费速率差和可承受时长，确认消费端慢、下游慢、分区倾斜还是故障。临时扩消费能力和隔离慢消息，长期优化消费批量/并发、分区与下游依赖；先保护 Broker 和数据库。

## Redis

### Q7：缓存与数据库如何保持一致？

**答题骨架**：Cache Aside：读未命中回源并写缓存；写以 DB 提交为事实来源，再删除缓存。删除失败靠有限重试和可靠补偿收敛；关键读绕过缓存或带版本。承认存在短暂窗口，不宣称绝对一致。

### Q8：分布式锁有哪些坑？

**答题骨架**：使用 `SET NX PX` 原子加带 TTL 的锁，value 是唯一 token；释放用比较 token 后删除的 Lua/原子命令，不能直接 `DEL`。主从异步复制有双持锁窗口；关键业务仍由 DB 条件更新、唯一约束或围栏令牌兜底。

### Q9：缓存击穿和雪崩的区别？

**答题骨架**：击穿是单热点 key 失效并发回源，用 single-flight/逻辑过期/预热；雪崩是大量 key 同时失效或 Redis 故障，用 TTL 抖动、限流、降级、多级缓存和隔离。两者都要保护数据库。

## MySQL

### Q10：如何设计联合索引？

**答题骨架**：从高频 SQL 的等值过滤、范围、排序和返回列出发；等值列常在前，范围列通常靠后，评估覆盖索引与写成本。用真实参数 `EXPLAIN` / 实际耗时验证，不只背最左前缀。

### Q11：RR 下 `FOR UPDATE` 为什么锁住很多行？

**答题骨架**：锁基于扫描的索引范围，默认 RR 的范围扫描可能采用 next-key lock；缺索引或非唯一/范围条件会扩大扫描。检查执行计划、缩小索引范围并保持短事务。

### Q12：写后读副本读到旧数据怎么办？

**答题骨架**：传统复制异步，旧读是正常风险。订单确认等读己之写场景读主库/会话粘滞，或等待副本追平；报表列表可接受延迟但要监控与降级。
