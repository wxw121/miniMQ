# 一致性、幂等与分布式事务

## 一分钟主线

“分布式系统中网络超时不等于失败，消息重复也很常见，所以我先定义业务事实来源和幂等键。跨服务流程通常拆成各自本地事务，通过 Outbox 可靠发布事件，再用幂等消费、状态机和补偿实现最终一致。只有确实需要同步强协调且资源支持时，才评估 2PC/TCC；多数订单类业务更适合可观测、可补偿的 Saga。”

## 先说清一致性语义

- **强一致/线性一致**：成功写后，后续读必须看到该写或更新的值；成本通常是等待、协调和可用性下降。
- **最终一致**：短时间内允许副本或下游状态不一致，但在无新变更、重试和补偿正常时收敛。
- **读己之写**：用户提交后马上查询，至少要看到自己的提交；常以写后读主库、会话粘滞或版本/位点等待实现。
- **业务一致性**：账户不能重复扣款、库存不能为负、订单状态不能回退等不变量。它常比“所有系统瞬时相同”更重要。

CAP 是发生网络分区时的取舍框架，不是“系统只能选两个”的日常口号。实际回答应落到场景：支付扣款宁可明确失败或处理中，不能假成功；商品推荐可返回稍旧数据以保持可用。

## 幂等：把“至少一次”变成“业务只生效一次”

幂等键应由业务语义确定，例如客户端请求 ID、支付流水号、订单号或消息唯一 ID；不要只用随机重试次数。常见实现：

| 层次 | 实现 | 边界 |
| --- | --- | --- |
| HTTP/API | `Idempotency-Key` 映射请求摘要与结果 | 要处理同 key 不同参数、处理中/超时状态和过期策略 |
| 数据库 | 业务唯一索引 + 事务内写处理记录 | 最终事实防线；要区分重复与并发冲突 |
| 消费者 | 消息 ID 去重表/Inbox + 业务状态机 | 去重记录和业务写入应同本地事务 |
| 下游调用 | 幂等 token 或资源版本/围栏令牌 | 下游必须真正校验，调用方单独缓存不够 |

示例：创建订单事务内插入 `orders(request_id unique)`；重复请求命中唯一约束后读取已存在订单并返回同一结果。若收到 MQ 重复消息，消费者在本地事务中先写入 `processed_messages(message_id unique)` 再推进订单状态；唯一冲突表示已处理而非重新执行业务。

## 为什么需要 Transactional Outbox

本地数据库提交与向消息代理发送事件是两个独立动作。先发消息再提交数据库，消费者可能看到未提交/最终回滚的数据；先提交数据库再发消息，进程在两者间崩溃会丢事件。Transactional Outbox 的做法是把业务变更和待发布事件写进**同一个本地事务**；后台发布器轮询或 CDC 读取 outbox，将事件投递到 MQ，成功后标记。它避免了数据库与消息代理之间的 2PC，但投递器仍可能重复发送，因此消费者必须幂等。[模式说明](https://microservices.io/patterns/data/transactional-outbox)

```text
订单服务本地事务：orders 状态变化 + outbox(order-created, eventId)
                         ↓ 提交
发布器/CDC：读取 outbox → 投递 MQ → 标记已发布（允许重复投递）
                         ↓
库存服务：Inbox 去重 + 本地库存事务 + 后续事件
```

Outbox 表需要索引、分批拉取、重试、积压监控、清理/归档与顺序策略。若同一聚合事件必须有序，按聚合 ID 分区/串行发布；不能以全局单线程换取“绝对顺序”。

## Saga、TCC 与 2PC 的选择

| 方案 | 适用 | 代价与边界 |
| --- | --- | --- |
| Saga（编排或协同） | 长流程、服务自治、可补偿业务 | 中间态可见；必须定义补偿、超时、幂等和人工介入 |
| TCC | 资源可预留，且参与者能实现 Try/Confirm/Cancel | 接口侵入大；空回滚、悬挂、幂等与资源冻结都要处理 |
| 2PC/XA | 少量、强协调需求且资源和运维可控 | 阻塞、耦合与可用性成本高，不是默认方案 |
| 本地事务 + Outbox | 大多数事件驱动业务 | 最终一致；消费者幂等和可观测性是必需项 |

Saga 的每个步骤是独立本地事务，失败后执行语义上的补偿，而不是数据库物理回滚。例如“取消预留库存”是补偿；已发放优惠券若无法撤回，可能需要创建反向权益或转人工。补偿同样必须幂等。[Saga 模式](https://microservices.io/patterns/data/saga.html)

## 状态机比“if-else 重试”更可靠

对订单可显式建模：`CREATED → STOCK_RESERVED → PAID → COMPLETED`，失败路径如 `STOCK_FAILED`、`CANCELLED`、`REFUNDING`。每次迁移以当前状态为条件更新，携带事件 ID/版本；超时扫描只处理仍处于对应中间态的记录。这样重复消息、乱序事件、超时重试和人工修复都有清晰边界。

## 与 MiniMQ 的可信映射

项目已具备持久化、确认/重投和恢复语义，可用于解释为何消费者必须幂等、为什么“至少一次”不等于重复执行一次业务。跨服务 Outbox/Saga 是生产业务落地方案，不是项目中已实现的功能；回答时应明确区分。

## 追问速答

**消息到底一次能做到吗？** 端到端“只处理一次”通常不靠传输层承诺，而是“至少一次投递 + 幂等消费者 + 业务唯一约束/状态机”。要说清系统边界和事实来源。

**超时后该重试吗？** 超时代表未知结果。先查幂等记录/资源状态；仅对可重试错误、在截止时间和重试预算内做指数退避加抖动，不能对非幂等写盲重试。

**如何处理重复扣款？** 支付流水号唯一约束与支付渠道幂等 token 是底线；订单状态转移在事务内进行。超时先查询渠道结果，不直接再次扣款；对账和补偿处理极端不一致。
