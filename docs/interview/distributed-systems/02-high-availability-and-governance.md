# 高可用、治理与可观测性

## 一分钟主线

“可用性不是无限重试或无限扩容。首先设定端到端超时、并发和队列上限，让故障快速失败；再按业务等级限流、舱壁隔离、熔断和降级，保护核心链路。所有保护都要有指标、追踪和演练验证：知道哪个依赖慢、重试是否放大流量、降级是否真的可用。”

## 超时、重试、隔离的正确顺序

1. **超时/截止时间**：从入口分配总预算，向下游传递剩余预算；连接、读写、排队和业务执行不能只设一个模糊超时。
2. **重试**：只重试临时性且幂等的失败；有限次数，指数退避加随机抖动，并设置全局/服务级 retry budget。
3. **隔离（bulkhead）**：不同下游、核心/非核心业务使用独立线程池、连接池、队列和并发阈值，避免一个依赖耗尽全部资源。
4. **熔断**：失败/慢调用超过阈值后快速拒绝或走降级，半开阶段用少量探测恢复；熔断状态和阈值必须可观测、可配置。
5. **限流与负载丢弃**：按租户、用户、接口、成本或优先级限制，过载时尽早、低成本地拒绝非关键请求。

Spring Cloud CircuitBreaker 为 Resilience4J、Spring Retry 等实现提供统一抽象；实际项目仍要明确每个依赖的超时、重试和降级语义，而非只加一个注解。[官方文档](https://docs.spring.io/spring-cloud-circuitbreaker/docs/current/reference/html/)

## 为什么“重试”会引发雪崩

依赖已经过载时，超时请求的重试会进一步增加入站量；如果网关、服务和客户端多层都重试，单个用户请求会被倍数放大。Google SRE 建议随机指数退避、限制单请求次数，并考虑服务级重试预算；这也是为什么需要在一个明确层级集中重试，而不是各层都重试。[级联故障指南](https://sre.google/sre-book/addressing-cascading-failures/)

## 限流选型

| 算法 | 特点 | 适用 |
| --- | --- | --- |
| 固定窗口 | 简单，但窗口边界可能突刺 | 低精度保护 |
| 滑动窗口 | 更平滑，需更多状态/计算 | API 配额与风控 |
| 漏桶 | 平滑输出、抑制突发 | 下游固定处理能力 |
| 令牌桶 | 平均速率受控，允许有限突发 | 常见接口保护 |
| 并发数限制 | 直接保护慢依赖和线程池 | RPC/DB 等等待型资源 |

限流不是只返回 429：要定义优先级（核心下单优于报表）、配额归属、失败提示/稍后重试、观测指标和误杀申诉路径。分布式限流常以 Redis/Lua 或网关实现，但 Redis 故障时需定义 fail-open / fail-close，安全接口和体验型接口的选择不同。

## 降级与故障转移

- **降级**：非核心推荐返回缓存或默认内容；统计/画像异步化；核心写请求宁可明确“处理中/稍后重试”，不能伪造成功。
- **熔断**：是对故障依赖的主动隔离；降级是熔断后的业务行为。二者不等同。
- **故障转移**：切流前确认目标容量、依赖就绪和数据一致性。一次性全量切换会将局部故障扩散；采用灰度、权重和回滚开关。
- **容量**：压测不仅看平均 QPS，要测尖峰、缓存冷启动、依赖变慢、节点丢失和恢复期。过载时系统应有限拒绝而不是线程/队列无限堆积。

## 可观测性：指标、日志、追踪三位一体

OpenTelemetry 将 traces、metrics、logs 作为核心信号；trace 记录请求跨服务路径，metric 适合聚合趋势和告警，log 记录离散事件。通过 `traceId`、`spanId`、业务 requestId 和语义化标签关联三者，但不要把用户 ID、完整 URL 或订单 ID 直接作为高基数 metric 标签，避免监控系统自身内存/成本失控。[信号模型](https://opentelemetry.io/docs/concepts/signals/) [指标基数说明](https://opentelemetry.io/docs/concepts/signals/metrics/)

建议最小观测集合：

- **黄金指标**：请求量、错误率、延迟分位数、饱和度（线程池、连接池、队列、CPU/内存）。
- **依赖指标**：下游调用成功率、超时、重试、熔断状态、数据库连接/慢查询、MQ 积压与消费延迟。
- **业务指标**：下单成功率、支付回调延迟、库存预留失败、Outbox 未发布量、补偿任务积压。
- **链路**：入口携带 requestId/trace context；异步消息把 trace/业务关联 ID 放入 header，消费者创建延续链路或可检索的关联记录。

## 线上故障处置模板

```text
确认影响与告警 → 冻结高风险变更 → 保护（限流/熔断/降级/切流）
→ 用指标缩小组件 → 用 Trace 定位依赖 → 用日志确认异常 → 小步修复/回滚
→ 验证恢复与积压消化 → 复盘、告警与演练改进
```

复盘关注系统性改进，不归咎个人：时间线、用户影响、触发条件、缓解措施、根因、未能更早发现的信号和有负责人/截止日的行动项。
