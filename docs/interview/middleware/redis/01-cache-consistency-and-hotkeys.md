# 缓存一致性与热点治理

## 一分钟主线

“我把 Redis 定位为数据库前的加速层。读路径优先 Cache Aside；写路径以数据库提交为事实来源，再删除缓存而不是直接改缓存。对短暂不一致，通过重试删除、消息/任务补偿和读端可接受窗口治理。高并发异常要先判断是穿透、击穿还是雪崩，再分别做数据拦截、单飞重建和流量削峰。”

## Cache Aside：最常用的读写路径

```text
读：Redis 命中 → 返回
读：Redis 未命中 → 查询 DB → 写入 Redis（带 TTL）→ 返回

写：更新 DB（事务提交）→ 删除 Redis key → 返回
```

### 为什么更新后删除，而不是更新缓存

- 删除更简单：下次读自然从数据库重建，避免多个写操作并发覆盖缓存。
- 更新缓存仍会面对写 DB 失败、序列错乱、字段部分更新与缓存写失败。
- 代价是删除到下一次读之间会回源；高频写 key 需结合限流、预热或异步重建评估。

### 不一致窗口怎样回答

先更新数据库再删除缓存，通常窗口来自“删除失败”或并发读在更新前读到旧值并在删除后回写旧缓存。我的治理顺序是：

1. 数据库事务成功后删除缓存；删除失败立即有限次重试并记录指标。
2. 将失效事件写入可靠消息或补偿任务，持续重试直至成功/人工告警。
3. 关键写操作给缓存值加版本或逻辑过期时间，避免旧回填覆盖新值。
4. 对强一致要求的少数读，绕过缓存直接读主库，或在写后短时间走受控读路径。

“延迟双删”可降低特定旧回填概率，但不是一致性保证：延迟时间难以覆盖所有慢查询，也会增加写放大。因此不能把它当作唯一方案；若使用，必须说清它只是补充，并由可靠失效补偿兜底。

## 三类缓存异常

| 问题 | 现象与根因 | 首选措施 | 补充措施 |
| --- | --- | --- | --- |
| 缓存穿透 | 不存在的 key 每次都访问 DB | 参数校验、缓存空值（短 TTL） | 布隆过滤器；限制查询频率 |
| 缓存击穿 | 一个热点 key 过期，大量请求同时回源 | 互斥重建 / single-flight | 逻辑过期后后台刷新；热点预热 |
| 缓存雪崩 | 大量 key 同时失效或 Redis 故障 | TTL 加随机抖动、限流/熔断 | 多级缓存、降级页、隔离与容量冗余 |

### 穿透

空值缓存须区分“确实不存在”与“临时数据库异常”；后者不能写空值。布隆过滤器会有假阳性，不能作为“存在”的最终结论，但能用作“不存在则快速拒绝”的前置过滤。对攻击型流量还需鉴权、限速和审计。

### 击穿

互斥重建的关键是“双检”：未命中后抢一个短期重建锁；拿到锁后再次读缓存，仍未命中才查库并回填；未拿到锁的请求短暂退避后读缓存，不能无上限自旋。逻辑过期适合可接受旧数据的读多热点：前台返回旧值，只有一个后台任务异步刷新。

### 雪崩

TTL 随机化仅分散过期时刻，不能处理 Redis 整体不可用。业务侧还要限制回源并发、为非核心读提供默认值/稍旧数据、将数据库连接池和线程池隔离，防止缓存故障级联拖垮主库。

## 热 Key 与大 Key

### 热 Key

识别：命令慢日志、客户端 QPS、`INFO commandstats`、访问采样、热点 key 监控。处理：本地 Caffeine 二级缓存、热点预热、逻辑过期异步刷新、按业务拆分 key；若要分片，需先确认读写一致性与失效广播方案。不要盲目复制：多副本会放大失效复杂度。

### 大 Key

风险：网络传输、序列化、复制/AOF、过期或删除都会造成延迟尖刺；单线程执行也会放大阻塞。处理：

- 先通过 `MEMORY USAGE`、慢日志、`--bigkeys`（低峰使用）和业务指标定位。
- 将超大 Hash/List/Set/ZSet 按用户或时间分桶；分页读取，避免一次 `HGETALL`/大范围 `LRANGE`。
- 删除大 key 采用异步释放能力或分批删除，并在压测/低峰验证。
- 设置 key 大小、集合元素数和序列化体积的准入阈值。

## 内存与淘汰策略

缓存实例应设置 `maxmemory`，并依据访问模式选择 `maxmemory-policy`。纯缓存且热点明显时，`allkeys-lru` 或 `allkeys-lfu` 常是候选；核心状态和缓存不要混放，因为淘汰策略可能让核心数据写入报错或被错误逐出。Redis 官方说明 `volatile-*` 策略只淘汰设置 TTL 的 key；若没有此类 key，效果接近 `noeviction`。因此上线前需明确 key 的 TTL 约束，并观测 `evicted_keys`、命中率、内存碎片和命令拒绝数。

## 追问速答

**缓存与数据库能做到绝对强一致吗？** 不能仅靠常规 Cache Aside 做到。缓存和数据库是两个独立系统；我会明确业务允许的窗口，并用可靠失效、版本、重试与关键读绕缓存收敛风险。

**为什么不先删缓存再更新数据库？** 并发读可能在删后、数据库更新前读到旧库值并回填旧缓存。先提交数据库再删，旧回填概率更低，且可由失效补偿处理删除失败。

**TTL 设置多少？** 由数据时效、回源成本、容量和允许的不一致窗口共同决定；同类 key 加随机抖动，并通过命中率、回源 QPS、内存和过期峰值调参，不给脱离业务的固定数值。
