# 分布式锁与稳定性治理

## 分布式锁的边界

锁适合控制“同一资源的短时间并发执行”，例如避免重复触发一次报表生成或热点缓存重建。它不是数据库事务替身：涉及余额、库存、订单状态的正确性，仍需数据库条件更新、唯一约束、幂等键或状态机兜底。

## 单 Redis 实例的正确基本形态

获取锁：

```text
SET lock:order:123 <随机唯一令牌> NX PX <租约毫秒>
```

- `NX` 确保仅在 key 不存在时写入；`PX` 在同一条命令中设置过期时间，避免“加锁成功但设置 TTL 前宕机”。
- value 必须是每次获取锁生成的唯一令牌，不能只写固定值 `1`。
- 释放时必须“比较令牌后删除”且原子执行。Redis 8.4 可使用 `DELEX key IFEQ token`；更早版本用 Lua：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
end
return 0
```

不能直接 `DEL`：持锁线程若发生长 GC、网络暂停或业务超时，锁可能已过期并被其他请求获得；它恢复后直接删除会误删别人的锁。

## 租约、续期与失败处理

租约必须覆盖正常业务耗时并预留网络/GC 余量，但不能无限长。若任务耗时不可控，优先拆分任务、做幂等检查点或转异步队列；续期机制只能降低过期概率，不能证明执行者一直拥有锁。

使用 Redisson 等封装时，我会确认：

- watch dog 是否仅在客户端仍存活、连接正常时续期；进程暂停时并不能替业务“保有”锁。
- 业务执行前、关键写入前是否仍能检查租约/所有权。
- 获取失败采用有上限的随机退避；超时后返回“处理中”或转异步，不忙等。
- `finally` 释放只释放当前令牌拥有的锁；业务异常、超时和进程崩溃依赖 TTL 回收与幂等补偿。

## 主从、哨兵、Cluster 与 Redlock：不要过度承诺

Redis 主从复制是异步的。可能出现：客户端 A 在主节点成功加锁，复制尚未到从节点时主节点故障，从节点提升；客户端 B 又获得同一锁。因此“哨兵 + 主从切换”不能单独提供故障期间绝对互斥。

面试中我会按风险分层：

| 场景 | 方案与底线 |
| --- | --- |
| 缓存重建、可容忍极端重复 | 单实例/主从锁 + TTL、唯一令牌、幂等处理，承认故障窗口 |
| 单业务库内扣减 | 数据库条件更新（如 `stock > 0`）+ 幂等键，锁仅作减压 |
| 跨资源、高风险且必须排他 | 优先使用具备一致性语义的协调系统或围栏令牌（fencing token）；让下游拒绝旧令牌 |
| 多独立 Redis 节点锁 | 可讨论 Redlock 的多数派、时钟漂移与可用性代价，但不把它表述为万能强一致方案 |

围栏令牌的核心是单调递增编号：每次获得执行资格拿到更大的 token；写入数据库/下游时携带 token，下游拒绝比已见 token 更小的请求。这样即使旧执行者“复活”，也无法覆盖新执行者的结果。

## 持久化、高可用与集群

- **RDB**：定时快照，恢复快、文件紧凑，但故障可能损失上次快照后的写入。
- **AOF**：记录写操作并重放恢复，持久性更强但有写放大与重写成本；RDB 与 AOF 可组合。缓存场景可以不持久化，关键状态必须先评估恢复目标和数据权威来源。
- **哨兵**：处理主从监控和故障转移，不等于消除异步复制的丢写/双持锁窗口。
- **Cluster**：按 hash slot 分片并提供副本故障转移；跨 key 的原子多 key 操作必须在同一 slot，可用 `{user:42}` 这类 hash tag 让相关 key 同槽。它不保证强一致，故障时可能丢失已确认写。

## 线上排查清单

1. **先定影响面**：命中率、P95/P99、错误率、回源数据库 QPS、连接数与消费者/线程池饱和度。
2. **看 Redis 自身**：`INFO memory/stats/commandstats/replication`、`SLOWLOG GET`、延迟监控、`evicted_keys`、`expired_keys`、`blocked_clients` 与复制延迟。
3. **判定类型**：CPU 高可能是大命令/Lua；内存高可能是大 key、过期策略或复制缓冲；连接高要区分连接泄漏与突发流量。
4. **先保护主库**：限流、熔断、降级、本地缓存和隔离；再处理根因。避免线上随意 `KEYS *`、大范围删除或立即改淘汰策略。
5. **修复后验证**：回源曲线、淘汰数、延迟、错误率恢复，补充 key 规范、容量阈值和告警。

## 回答模板：如何设计秒杀库存

“Redis 可以做预扣和限流以承接流量，但库存正确性仍由数据库条件扣减或可靠库存服务保证。请求先校验幂等令牌和活动状态；Redis 原子脚本可防止同一瞬间超卖的前置请求，成功后异步创建订单。消费者以订单号去重，数据库用唯一约束/条件更新完成最终扣减；失败则补偿 Redis 预扣。这样 Redis 故障时可以降级为排队或拒绝，而不是让缓存成为唯一事实来源。”
