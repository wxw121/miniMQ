# Redis 场景题与速答卡

## 场景 1：商品详情缓存命中率突然下降，数据库 QPS 飙升

**回答框架**

1. 先确认 Redis 可用性、命中率、过期 key 数和业务发布/批量失效事件，区分 Redis 故障、TTL 集中过期与缓存代码退化。
2. 立刻保护数据库：对详情回源做限流与请求合并，非核心字段降级；热点走本地缓存或返回稍旧数据。
3. 若是集中过期，给 TTL 加抖动并预热核心商品；若是击穿，启用单飞重建或逻辑过期异步刷新。
4. 复盘容量、TTL 分布、失效事件和告警阈值，压测验证回源上限。

**加分点**：不先说“加机器”，先用指标确认瓶颈是否已传导到主库。

## 场景 2：用 Redis 锁防止重复下单，仍出现两笔订单

**可能原因**

- 锁租约短于业务耗时，旧线程与新线程重叠执行。
- 锁释放时直接 `DEL`，误删新持有者的锁。
- 主从故障转移前锁未复制，两个客户端分别获得锁。
- 只依赖锁，没有订单唯一约束/幂等键。

**整改**：锁使用 `SET NX PX + 唯一 token + 比较删除`；获取失败随机退避且有上限；订单表以业务幂等号建立唯一约束，创建订单使用事务；必要时用围栏 token 或换具备合适一致性语义的协调方案。锁只是前置减压，数据库约束才是最终防线。

## 场景 3：一个 50 MB 的用户画像 Hash 导致延迟尖刺

**回答**：先用慢日志、命令统计和 `MEMORY USAGE` 验证 key 及访问命令，不在线上跑会阻塞的大扫描。将画像按维度或时间拆 key，读取改为字段级/分页；删除使用异步释放或分批，避免主线程长时间阻塞。再给单 key 体积、集合长度、序列化大小设准入指标，并观察复制和 AOF 重写期间的延迟。

## 场景 4：Redis Cluster 故障转移后业务读到旧值

**回答**：Cluster 的副本复制是异步的，故障时可能损失已确认写，不应承诺强一致。若这是可缓存数据，短暂旧读应由 TTL、失效补偿和回源收敛；若是订单/余额等核心事实，读写必须以数据库或具备所需一致性保证的系统为准。还要检查客户端是否支持拓扑刷新与 `MOVED`/`ASK` 重定向，以及关联 key 是否通过 hash tag 保证同槽。

## 场景 5：缓存实例内存接近上限

**回答**：先区分数据集增长、复制/AOF 缓冲、内存碎片和连接输出缓冲；看 `used_memory`、`maxmemory`、淘汰数、命令拒绝数、大 key 和 TTL 分布。纯缓存选择与访问模式一致的淘汰策略，并确保缓存 key 有 TTL；核心状态与缓存隔离。临时扩容/限流保护后，再从 key 模型、过期策略和容量预算消除根因。

## 高频问答

### Redis 为什么快？

核心数据在内存；事件循环与高效数据结构减少常见路径开销。但不能简化成“单线程所以一定快”：大 key、大命令、阻塞 Lua、网络和持久化/复制都会形成延迟瓶颈。

### Redis 与本地缓存怎么分工？

本地缓存延迟更低、能抗 Redis 瞬时抖动，但多实例一致性与内存占用更难处理；Redis 适合跨实例共享。通常将极热点且可短暂陈旧的数据放本地二级缓存，并有 TTL、失效通知或版本策略；不能把本地缓存当作强一致存储。

### Lua 脚本为何有用，又有什么风险？

它能把多条 Redis 操作在服务器端原子执行，适合校验并扣减、比较并删除锁等短逻辑。风险是脚本执行时间过长会阻塞后续请求；脚本必须短小、避免大范围遍历和不可控外部依赖，并在压测中观察延迟。

### Redis 发生故障，怎样降级？

先按业务分级：非核心读返回默认值、稍旧数据或本地缓存；可异步的请求进入队列；核心写走数据库受控路径或明确失败，不能伪造成功。再用限流、熔断、超时和连接池隔离防止重试风暴压垮数据库。

### 是否在 MiniMQ 项目中落地过 Redis？

不虚构。当前 MiniMQ 的项目证据重点是 Java/NIO、协议、持久化、投递语义与测试；Redis 内容是我可迁移到生产业务的设计方法。我会先说明这点，再用上述场景说明自己如何落地、监控和验证。
