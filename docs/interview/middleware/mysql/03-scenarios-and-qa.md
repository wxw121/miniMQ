# MySQL 场景题与速答卡

## 场景 1：订单列表接口从 50 ms 变成 3 s

**排查与回答**

1. 确认范围：接口 QPS、P95/P99、错误率、发布变更、参数/租户分布，区分数据库慢、连接池等待还是下游慢。
2. 从慢日志/监控定位 SQL，拿真实且脱敏的高频参数执行 `EXPLAIN`，观察索引、估算扫描行和排序/临时表。
3. 检查条件是否匹配联合索引、是否出现深分页、函数/隐式转换、`SELECT *` 或返回过多行。
4. 做最小修复：加/调整索引、改为 seek 分页、减少列与结果集，或更新统计信息；压测并灰度验证延迟和写入代价。
5. 补齐慢 SQL、扫描行数、连接池和锁等待告警，防止回归。

## 场景 2：两个事务频繁死锁

**回答**：先接受死锁是数据库并发控制的正常结果，应用要能重试。用死锁日志与 SQL 参数还原锁顺序，检查是否多表/多行访问顺序不一致或缺索引扩大了锁范围。统一按主键顺序更新，缩短事务，拆小批量；对幂等事务有限次退避重试。若涉及外部调用，不能把它放进长事务，应改为可靠消息或补偿流程。

## 场景 3：`SELECT ... FOR UPDATE` 看起来锁住了不相关记录

**回答**：先看隔离级别和执行计划。InnoDB 的锁基于实际扫描的索引范围；默认 RR 下范围扫描会出现 next-key lock。若索引缺失或条件未命中唯一索引，扫描范围可能很大。通过合适索引、唯一等值条件、缩短事务降低影响；不能简单认为 `FOR UPDATE` 只锁最终返回的一行。

## 场景 4：写订单后读副本查不到新订单

**回答**：传统主从复制是异步的，副本延迟会导致旧读。对订单创建后的确认页执行读写路由粘滞，短时间读源库；或采用 GTID/位点等待副本追平。列表和报表可读副本，但要监控延迟并设置回源降级阈值。不能靠无限重试掩盖一致性要求不清。

## 场景 5：千万级表需要新增字段/索引

**回答**：先确定数据库版本、表大小、峰值写入、DDL 能力和回滚方案。评估 online DDL 是否仍有元数据锁与资源风险，选择低峰、限速、分批或在线变更工具；在预发按真实量级验证锁等待和复制延迟。发布前后监控 DDL 进度、主从延迟、错误率和磁盘；索引建成后再确认优化器真正使用，不把“创建成功”当作优化完成。

## 场景 6：什么时候分库分表？

分库分表不是单表行数达到固定阈值就启动。先穷尽查询/索引优化、冷热分离、归档、读写分离与容量扩展；当单库的存储、写入、索引维护、备份恢复窗口或热点已经成为明确瓶颈，再按访问路由选择分片键。设计时必须提前回答：全局 ID、跨分片查询、聚合、事务边界、扩容迁移、数据校验和运维复杂度。优先选择能让大多数核心查询单分片命中的键。

## 高频问答

### 为什么建议使用自增/趋势递增主键？

它通常使聚簇索引写入更集中，减少随机插入的页分裂；但分布式环境还需平衡全局唯一、可用性和业务暴露风险。不是禁止 UUID，而是要评估有序性、长度和二级索引膨胀。

### `EXPLAIN` 的 `rows` 很小就一定快吗？

不是。它通常是估算；还要看真实耗时、回表、排序、返回行数、锁等待、网络以及并发量。估算偏差大时检查统计信息和数据倾斜。

### 慢 SQL 应先加缓存吗？

先确认查询是否适合缓存及允许的陈旧窗口。索引缺失、扫描过大或事务锁等待应先修根因；缓存是降低重复读压力的手段，不应掩盖写路径或一致性问题。

### 如何避免重复消费/重复写订单？

用业务幂等号建立唯一约束，事务内写入订单/处理记录；消费者重试时识别重复并返回已有结果。消息投递通常至少一次，不能假设只会处理一次。
