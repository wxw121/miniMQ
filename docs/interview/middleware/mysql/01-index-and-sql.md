# 索引与 SQL 优化

## 一分钟主线

“索引服务于具体查询，不是给每个字段都建。我先从慢日志、调用频率和返回行数确定目标 SQL，再用 `EXPLAIN` / `EXPLAIN ANALYZE` 对照实际扫描行数与预期；根据 `WHERE`、关联、排序和分页设计联合索引，最后通过压测和线上指标验证读收益是否覆盖写放大。”

## InnoDB 索引的关键认知

- InnoDB 使用 B+Tree 组织常见索引。聚簇索引的叶子节点保存整行数据；二级索引叶子保存二级索引列及主键值。
- 因此二级索引查不到所需字段时，需要根据主键再定位聚簇索引，常称“回表”；若查询列都在索引中，就是覆盖索引，可减少该步骤。
- 主键宜短、稳定、递增趋势好；随机且很长的主键会放大二级索引体积和页分裂成本。具体选型仍取决于分布式 ID、写入模式和业务可见性。

## 联合索引：按查询而非按字段排序

常用思路：等值过滤列在前，范围列通常靠后，再考虑排序/分组和覆盖列。例如高频查询：

```sql
SELECT id, status, created_at
FROM orders
WHERE tenant_id = ? AND status = ? AND created_at >= ?
ORDER BY created_at DESC
LIMIT 50;
```

候选索引是 `(tenant_id, status, created_at)`，它能利用等值前缀加时间范围，并有机会按索引顺序返回。是否完全避免排序，还取决于排序方向、其他条件、选择性和优化器成本估算。

**最左前缀**：`(a, b, c)` 可以支持以 `a` 开始的查找，如 `a`、`a,b`、`a,b,c`；不能把它等价为单列 `b` 或 `c` 索引。范围条件之后的列未必不能使用，但常难以继续用于缩小索引扫描范围；应以真实执行计划为准。

## 常见索引失效/收益变差原因

| 情形 | 问题 | 改进方向 |
| --- | --- | --- |
| 对索引列做函数/运算 | 可能无法按原索引范围检索 | 改写条件，或评估函数索引/生成列 |
| 隐式类型转换 | 比较语义和索引选择可能变化 | 参数与列类型一致，避免字符串比数字 |
| 前置模糊匹配 | `LIKE '%abc'` 通常无法有效用普通 B+Tree 前缀 | 搜索引擎、倒排/全文索引，或调整需求 |
| `OR` 跨不同列 | 计划可能变差、扫描扩大 | 评估拆为 `UNION ALL`，注意去重语义 |
| 返回大量行 | 优化器可能选择全表扫描更低成本 | 限制结果集、调整查询模型，非盲目加索引 |
| 索引过多 | 写放大、空间和优化器选择成本 | 删除冗余/低收益索引，灰度验证 |

## 如何读 `EXPLAIN`

不是只看 `type`。我会将计划与业务目标一起看：

1. **访问对象与顺序**：`table`、连接顺序、`type`；警惕大表 `ALL`，但小表或高比例扫描不必机械判错。
2. **候选与实际索引**：`possible_keys`、`key`、`key_len`，确认索引确实按预期前缀参与。
3. **扫描与过滤**：`rows`、`filtered` 是估算值；结合实际执行时间、慢日志与 `EXPLAIN ANALYZE`（适用版本）验证估算偏差。
4. **额外操作**：`Extra` 中的 `Using filesort`、`Using temporary` 是继续分析信号，不是绝对错误；`Using index` 往往说明覆盖索引。
5. **统计信息**：若计划与真实分布长期偏离，先检查统计信息并在合适窗口 `ANALYZE TABLE`，再谨慎考虑 hint。

## 慢 SQL 排查闭环

```text
告警/慢日志 → 关联接口与参数分布 → 复现 SQL → EXPLAIN/实际耗时
→ 最小改写（索引、SQL、分页或数据模型）→ 压测 → 灰度 → 监控回归
```

排查时同时看 QPS、P95/P99、扫描行数、返回行数、锁等待、CPU/IO、连接池等待。单条 SQL 本身不慢也可能因为高并发、热点参数或事务持锁而拖垮系统。

## 分页

`LIMIT offset, size` 在大 offset 时通常需要跳过前面很多行。按稳定且有索引的排序键做**游标/seek 分页**更适合深翻页：

```sql
SELECT id, created_at, status
FROM orders
WHERE tenant_id = ?
  AND (created_at < ? OR (created_at = ? AND id < ?))
ORDER BY created_at DESC, id DESC
LIMIT 50;
```

对应索引需围绕 `tenant_id, created_at, id` 及排序方向和版本能力验证。对需要跳页、任意页码的后台场景，仍可能选择 offset，但要设页数上限或走异步导出。

## 追问速答

**为什么不是索引越多越好？** 每个索引都要维护，会增加写放大、磁盘和 buffer pool 压力，也可能让优化器选择更复杂。以高频、选择性和关键查询为依据，并定期清理冗余索引。

**何时考虑覆盖索引？** 高频读、返回列少且回表代价明显时；但不能为了覆盖把过多低选择性字段塞入索引，需衡量索引体积与写成本。

**能否强制索引？** 先证实统计信息或成本估算导致的错误计划，优先更新统计或改写 SQL。`FORCE INDEX` 是受控兜底，需版本化、压测与持续观测，不能当默认修复。
