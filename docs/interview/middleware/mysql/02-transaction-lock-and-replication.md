# 事务、锁与复制

## ACID 与事务边界

- **原子性**：事务内操作要么全部提交，要么全部回滚。
- **一致性**：应用约束、数据库约束和事务共同维护业务不变量；它不是“不会读到旧数据”的同义词。
- **隔离性**：并发事务的可见性与互相影响由隔离级别、MVCC 和锁决定。
- **持久性**：已提交事务在故障后可恢复，依赖日志与刷盘策略，仍要按 RPO/RTO 设计备份与演练。

事务应短小：只包住必须原子化的数据库操作；不要在事务中做远程调用、长计算或等待用户输入。外部副作用需通过 outbox、可靠消息、幂等消费或补偿模式衔接，而不是期望跨系统大事务解决一切问题。

## 隔离级别与 MVCC

InnoDB 支持读未提交、读已提交、可重复读、串行化，默认是 **REPEATABLE READ (RR)**。普通一致性读通常通过 MVCC 从版本链和 Read View 获取可见版本，不必加锁；锁定读、更新和删除则读取较新的记录并加锁。

| 隔离级别 | 核心特征 | 典型取舍 |
| --- | --- | --- |
| READ UNCOMMITTED | 可读到未提交变更 | 很少用于核心业务 |
| READ COMMITTED | 每次一致性读可获得新快照 | 减少部分范围锁影响，但同一事务内可重复读性较弱 |
| REPEATABLE READ | 同一事务普通读通常复用首个读建立的快照 | InnoDB 默认；范围锁行为需结合 SQL 与索引理解 |
| SERIALIZABLE | 更严格并发控制 | 吞吐下降，少数特殊场景使用 |

不要笼统说“RR 完全不会幻读”。普通快照读与锁定读的行为不同；在默认 RR 下，索引范围的锁定读/更新常通过 next-key lock 阻止范围内插入。面试中应先确认是普通 `SELECT`、`SELECT ... FOR UPDATE` 还是 `UPDATE/DELETE`，再讨论现象。

## 锁：记录锁、间隙锁、Next-Key Lock

- **记录锁**：锁住某条索引记录。
- **间隙锁**：锁住索引记录之间的区间，阻止其他事务在该间隙插入。
- **Next-Key Lock**：记录锁 + 前面的间隙锁。InnoDB 默认 RR 的范围扫描常用它降低幻读风险。

锁基于**实际扫描到的索引记录/范围**，不只看最终 WHERE 是否返回该行。因此缺合适索引的更新或锁定读可能扫描更大范围，导致“看起来只改一行却锁了很多行”。唯一索引的等值命中通常能缩小到记录锁；非唯一或范围查询需要按实际条件与计划分析。

## 死锁：接受、缩小、重试

死锁不可完全消除，应用必须能识别并重试被回滚的事务。处理顺序：

1. 在日志/监控中捕获死锁错误，保留 SQL、参数和事务链路；用 `SHOW ENGINE INNODB STATUS` 或 Performance Schema 分析等待环。
2. 统一多表/多行更新的访问顺序，例如始终按主键升序锁定。
3. 使用合适索引缩小扫描和锁范围，拆短事务，减少批量更新量。
4. 对可安全重试的事务做有限次数随机退避重试；依靠幂等键或唯一约束防止重试产生重复副作用。

不要用无限重试掩盖问题；频繁死锁应按业务热点、SQL 和索引根因治理。

## 库存扣减的正确性

```sql
UPDATE sku_stock
SET available = available - ?
WHERE sku_id = ? AND available >= ?;
```

根据受影响行数判断是否扣减成功。它将“库存不能为负”编码为单条数据库原子条件更新；订单侧再用请求幂等号唯一约束，避免客户端重试重复创建订单。Redis 锁可降低热点竞争，但不应作为超卖防线的唯一依据。

## 主从复制与读写一致性

传统 source-replica 复制中，源库提交后，变更再异步发送给副本，因此读副本可能有延迟：写后立刻读到旧值是预期风险，而非偶发现象。

| 业务要求 | 做法 |
| --- | --- |
| 可接受短暂旧读的列表/报表 | 读副本，监控复制延迟，超过阈值降级到源库或返回稍旧结果 |
| 写后立即确认的订单状态 | 写后读源库；或按 GTID/位点等待副本追平后再读 |
| 强一致核心判断 | 固定读写源库或使用满足一致性需求的架构，不靠“多读几次副本” |

复制还要关注 binlog、relay log、延迟、错误和故障切换后的只读策略。备份不是复制的替代；应独立做全量/增量备份、恢复演练和权限校验。
