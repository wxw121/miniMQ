# 场景题与高频问答

## 场景 1：订单创建后要通知库存、积分、物流，如何设计？

**回答框架：**

1. 订单服务本地事务写订单与 outbox 事件；异步投递器可靠发布 `OrderCreated`。
2. 以 `orderId` 作为 key，保证同一订单内事件到同一分区/队列；不要要求全局顺序。
3. 下游以 `eventId` 或业务唯一键去重，采用状态机/条件更新，能承受至少一次重投。
4. 重试分级：瞬时错误退避重试；不可恢复错误入 DLQ；必须有告警、查询和补偿入口。
5. 监控 publish failure、consumer lag、retry/DLQ 数、处理耗时和端到端延迟。

**追问：** “为什么不用数据库事务直接写所有服务？”  
**答：** 跨服务强事务会扩大耦合和可用性风险。Outbox + 最终一致性把本地一致性缩小到单库事务，再用幂等和补偿处理异步边界。

## 场景 2：支付成功消息绝不能漏，也不能重复扣款

**回答框架：**

- “绝不能漏”先定义边界：支付核心状态必须先落在支付库；消息只用于异步通知或对账，不应作为唯一事实来源。
- 以支付流水号为幂等键；扣款/退款使用状态机和唯一约束/条件更新，重复消息只返回已有结果。
- Producer 使用可靠投递（outbox 或 RocketMQ 事务消息取决于栈）；Broker ack 与副本只是其中一层。
- 消费失败重试后进入 DLQ；DLQ 不是终点，要能查、修、补、回放并审计。

**不要说：** “用了 MQ 就 exactly once。”

## 场景 3：消息积压数千万，先做什么？

1. 确认生产速率、消费速率、lag 增长速度、消息大小、失败率和下游瓶颈。
2. 先止血：限流/降级非核心生产者、扩消费实例、提高批量并行度；若受 partition/queue 限制，先扩并行单元并评估数据迁移与 key 顺序影响。
3. 排除 poison message、重试风暴、单分区热点、慢 SQL/外部 RPC、GC 和线程池耗尽。
4. 恢复时控制并发和下游压力，避免“消费者扩容把数据库打垮”。
5. 复盘：容量水位告警、lag SLO、压测基线、限流预案和 DLQ 处理时限。

## 场景 4：怎样保证订单内消息顺序？

用 `orderId` 作为 sharding key，使同一订单落到同一 partition/MessageQueue；消费者对该局部队列串行处理或用同 key 的有序执行器。必须接受：跨订单不保证顺序；热点订单会限制并行度；重试和失败转移也要保持同 key 的有序策略。

## 场景 5：消费者处理成功但提交 offset 前宕机怎么办？

消息会再次投递，这是至少一次的正常结果。处理逻辑要幂等：以 eventId/业务号建立唯一约束，或用“只有状态为待处理才更新”的条件更新；提交 offset 应在业务持久化成功后。不要用“先提交 offset”逃避重复，因为那会扩大丢消息窗口。

## 场景 6：Kafka 与 RocketMQ 怎么选？

不先报结论，先问：事件流还是业务消息？是否需要既有生态/流计算？顺序、延时、事务消息、重试治理的需求是什么？团队已有集群与运维能力如何？

然后给倾向：Kafka 常适合分区日志和流处理生态；RocketMQ 对交易型业务消息的顺序、事务、延时及 retry/DLQ 治理常更直接。最终看 SLA、运维成本和一致性边界，而不是参数对比表。

## 速答卡

| 问题 | 20 秒回答 |
| --- | --- |
| 为什么不能保证全局顺序？ | 全局单队列会把并行度降为 1；大多数业务只需要订单/账户等 key 范围内有序。 |
| 重复消费怎么处理？ | 业务幂等，不能依赖 MQ “不重复”；唯一键、状态机、条件更新和去重记录任选组合。 |
| 重试为什么要 DLQ？ | 防止不可恢复消息无限阻塞/放大流量；DLQ 让人工修复和受控回放成为可观测流程。 |
| 什么时候扩 consumer 不生效？ | consumer 数超过 partition/queue 数、热点集中、下游瓶颈或失败重试占满容量时。 |
| ack=all 是否一定不丢？ | 它只描述当前 ISR 的确认条件；还要看 flush、复制、故障模型与业务外部副作用。 |
| 如何减少 rebalance 影响？ | 控制实例频繁伸缩、避免超过 session/poll 预算的长处理、合理提交 offset，并把重任务拆分。 |

## 练习法

每题按“结论 → 方案 → 失败路径 → 可观测性 → 取舍”讲 90 秒。随后把其中一个点映射到 [MiniMQ 项目证据](02-minimq-mapping.md)，但只讲自己能解释和实际参与的模块。
